## 软件工程的定义与目标

软件工程是把系统化、规范化、可度量的方法应用于软件开发、运行与维护的学科。它的提出源于软件危机：硬件性能快速提升，软件规模迅速扩大，而开发方式仍停留在个体手工作业，导致项目普遍延期、超支、缺陷密集、难以维护。

软件危机的典型表现包括：

- 需求在开发后期仍频繁变化，已完成的工作大量返工；
- 项目进度与成本无法准确估算；
- 软件质量依赖个别开发者的经验，缺少可重复的过程；
- 文档缺失，维护人员只能通过阅读代码理解系统；
- 缺陷发现得越晚，修复成本越高。

软件工程的目标不是消除复杂性，而是把复杂性控制在可管理的范围内。为此形成了三要素：方法、工具与过程。方法提供分析与设计的思维框架，工具提供自动化支持，过程规定活动之间的顺序、输入、输出与评审点。

软件质量通常从多个维度衡量。ISO/IEC 25010 给出的质量模型包括功能适合性、性能效率、兼容性、易用性、可靠性、安全性、可维护性与可移植性。不同系统对这些属性的优先级不同，需求分析阶段需要明确取舍，而不是笼统地要求高质量。

## 软件生命周期

软件生命周期指软件从提出需求到停止使用的全部过程。面向过程方法通常把生命周期划分为以下阶段：

| 阶段 | 主要任务 | 主要交付物 | 评审重点 |
| :--- | :--- | :--- | :--- |
| 可行性研究 | 判断项目是否值得做、能否做 | 可行性研究报告 | 技术路线、成本、收益、风险 |
| 需求分析 | 明确系统必须做什么 | 需求规格说明书 | 完整性、一致性、可验证性 |
| 概要设计 | 确定系统结构、模块划分与接口 | 概要设计说明书 | 模块独立性、接口清晰度 |
| 详细设计 | 确定每个模块的内部算法与数据结构 | 详细设计说明书 | 算法正确性、可读性 |
| 编码实现 | 把设计转换为程序 | 源代码、单元测试记录 | 规范符合度、静态检查结果 |
| 测试 | 发现并修复缺陷 | 测试计划、测试用例、测试报告 | 覆盖率、缺陷收敛趋势 |
| 运行与维护 | 部署、监控、修改与演进 | 维护记录、版本说明 | 变更受控、回归验证 |

阶段划分的意义在于把大问题分解为可管理的小问题，并在每个阶段结束时设置评审点。评审通过后形成的文档与代码构成基线，后续修改必须经过变更控制。基线的作用是保证团队对当前版本有共同、确定的认知。

阶段之间并非严格的线性关系。需求分析发现可行性问题时需要回到上一阶段，测试发现设计缺陷时需要回溯修改。生命周期模型决定这些回溯如何组织，后文单独讨论。

## 可行性研究

可行性研究在投入大量资源之前回答三个问题：问题是否值得解决，方案是否能够实现，实施后是否产生足够收益。

### 可行性分析的维度

- **技术可行性**：现有技术栈、团队能力、性能指标是否支持方案落地。需要识别关键技术风险，必要时先做原型验证。
- **经济可行性**：估算开发成本、运行成本与预期收益。常用指标包括投资回收期、净现值与投资回报率。
- **操作可行性**：组织结构、业务流程与用户习惯是否接受新系统。技术可行的系统可能因为流程冲突而无法推广。
- **法律与合规可行性**：数据采集、隐私保护、许可协议与行业监管是否允许系统按设计运行。

### 成本估算

成本估算在项目早期只能基于不完整信息进行，因此需要明确假设与误差范围。常用方法包括：

- **代码行估算**：按功能模块估算代码规模，再乘以单位规模的生产成本。方法简单，但对新技术与新团队误差较大。
- **功能点估算**：按输入、输出、查询、文件与接口的数量估算功能规模，与实现语言无关。
- **类比估算**：参考历史相似项目的实际成本，按规模与复杂度调整。
- **专家判断与三点估算**：给出乐观、最可能、悲观三个值，按加权公式计算期望成本。

估算结果应随项目进展持续修正。把早期估算当作承诺，是项目失控的常见原因。

### 可行性研究报告

报告通常包含背景与目标、候选方案、技术方案、成本与收益、风险与对策、结论与建议。结论可以是立即实施、延期实施、缩小范围实施或放弃。可行性研究的价值在于尽早终止不值得投入的项目，而不是为已经决定的方案补写材料。

## 需求分析

需求分析确定系统必须提供什么行为，以及必须满足什么约束。它不讨论如何实现，只讨论外部可见的行为与质量要求。

### 需求的分类

- **功能需求**：系统必须完成的处理，例如录入成绩、统计平均分、按姓名查询。
- **非功能需求**：性能、可靠性、安全性、易用性、可维护性等质量约束，例如查询响应时间不超过 1 秒。
- **约束条件**：技术栈、运行环境、法规、接口协议等外部限制。

需求必须可验证。诸如界面友好、运行稳定之类的要求无法直接验收，需要转化为可测量的指标，例如常用操作不超过三次点击、系统可用性达到 99.5%。

### 结构化分析

面向过程方法使用结构化分析建立系统的功能模型与数据模型。常用工具包括：

- **数据流图（Data Flow Diagram，DFD）**：描述数据在系统中的流动、加工与存储。
- **数据字典**：定义 DFD 中每个数据流、数据元素与数据存储的组成与取值范围。
- **实体联系图（ER 图）**：描述数据实体及其关系。
- **状态转换图**：描述系统或对象在事件驱动下的状态变化。

DFD 采用自顶向下的分解方式。顶层图把整个系统视为一个加工，只画外部实体与系统之间的输入输出；逐层分解时，父图的加工被展开为子图，输入输出必须保持平衡。

以学生成绩管理系统为例，顶层图如下：

```text
           成绩文件
              |
              v
学生 ----> [成绩管理系统] ----> 成绩报表
              ^
              |
            教师
```

第一层分解为三个加工：

```text
学生 --成绩记录--> [1 录入成绩] --合法记录--> [D1 成绩表]
教师 --查询条件--> [2 统计查询] <--读取-------- [D1 成绩表]
教师 <--报表------ [3 输出报表] <--统计数据---- [2 统计查询]
```

数据字典为每条数据流给出定义，例如：

```text
成绩记录 = 学号 + 姓名 + 分数
学号     = 8{数字}8
姓名     = 2{汉字}4
分数     = 0.0 .. 100.0
```

数据字典的作用是消除歧义。仅凭图形无法确定学号的长度、姓名的范围与分数的合法区间，这些约束必须在字典中写清楚，并在后续设计与测试中沿用。

### 需求规格说明书

需求规格说明书是需求阶段的基线文档，通常包含：

1. 引言：目的、范围、术语、参考文档；
2. 总体描述：用户特征、运行环境、约束与假设；
3. 功能需求：按用例或加工逐项编号，给出输入、处理与输出；
4. 非功能需求：性能、可靠性、安全性与可维护性指标；
5. 外部接口：文件格式、网络协议、硬件接口；
6. 验收标准：每项需求的验证方法。

需求条目应当编号并可追踪。设计文档引用需求编号，测试用例引用需求编号，变更时才能评估影响范围。

### 需求评审

需求评审的目标是在进入设计之前发现遗漏、冲突与不可实现的条目。评审应包含用户代表、开发人员与测试人员。常见问题包括：只描述正常流程而忽略异常分支；功能之间存在隐含依赖；非功能指标缺失；术语在文档中前后不一致。

评审通过后，需求进入基线。此后的需求变更需要评估工作量、风险与交付时间，并更新相关设计与测试文档。
## 概要设计

概要设计把需求转换为软件结构，确定模块划分、模块职责、调用关系与接口。它回答系统由哪些部分组成、各部分如何协作，不涉及模块内部的算法细节。

### 模块化

模块是功能独立、可单独命名与调用的程序单元。模块化把复杂系统分解为若干规模较小、职责单一的部分，使开发、测试与维护可以并行进行。

模块划分并非越细越好。模块数量增加会带来接口数量与调用开销的增加，模块过少则单个模块过于复杂。合理的划分应当使每个模块内部联系紧密、模块之间联系松散。

### 耦合

耦合衡量模块之间相互依赖的程度。耦合越低，模块越容易独立修改与复用。常见的耦合类型按依赖程度由低到高排列如下：

| 耦合类型 | 含义 | 示例 |
| :--- | :--- | :--- |
| 非直接耦合 | 模块之间没有直接联系 | 两个模块通过主模块调度，彼此不引用 |
| 数据耦合 | 通过参数传递简单数据 | 调用排序函数时传入数组与长度 |
| 标记耦合 | 通过参数传递数据结构，但只使用其中部分字段 | 传入完整学生记录，函数只读取分数 |
| 控制耦合 | 传递控制信息，影响被调用模块的执行路径 | 传入布尔标志决定是否打印明细 |
| 外部耦合 | 依赖外部环境、文件格式或设备约定 | 多个模块直接读写同一个文件格式 |
| 公共耦合 | 多个模块共享全局数据区 | 使用全局变量保存配置与状态 |
| 内容耦合 | 一个模块直接访问另一个模块的内部数据或代码 | 直接修改另一模块的静态变量 |

设计目标是尽量使用数据耦合，避免控制耦合、公共耦合与内容耦合。标记耦合在参数为结构体时难以完全避免，但应限制被调用模块只读取必要的字段。

### 内聚

内聚衡量模块内部各成分之间的关联程度。内聚越高，模块职责越集中。常见的内聚类型按强度由高到低排列如下：

| 内聚类型 | 含义 | 示例 |
| :--- | :--- | :--- |
| 功能内聚 | 所有成分共同完成单一功能 | 计算平均分 |
| 顺序内聚 | 各成分按固定顺序执行，前一步输出是后一步输入 | 读取成绩后立即排序 |
| 通信内聚 | 各成分操作同一组数据 | 对同一数组求最大值与平均值 |
| 过程内聚 | 各成分按特定控制流程执行，彼此数据联系较少 | 初始化、处理、清理三个步骤 |
| 时间内聚 | 各成分因在同一时间段执行而被放在一起 | 系统启动时的多项初始化 |
| 逻辑内聚 | 各成分功能相似，通过参数选择执行哪一个 | 一个函数根据类型参数打印不同报表 |
| 偶然内聚 | 各成分之间没有实质联系 | 把无关的工具函数放入同一文件 |

高内聚与低耦合通常同时追求，但二者可能冲突。把功能拆得过细会降低内聚，把多个功能合并会提高耦合。设计需要在两者之间取得平衡。

### 模块结构图

模块结构图描述模块之间的调用关系。图中每个方框代表一个模块，箭头表示调用，旁边可以标注参数与返回值。

```text
                成绩管理
        ┌───────────┼───────────┐
     输入模块     处理模块     输出模块
        │            │            │
   读取文件       排序统计      打印报表
   校验数据       计算指标      按姓名查询
```

结构图的辅助指标包括：

- **深度**：从顶层到最底层的层数；
- **宽度**：同一层中模块的最大数量；
- **扇出**：一个模块直接调用的下级模块数量；
- **扇入**：一个模块被多少个上级模块调用。

扇出过大说明该模块职责过重，扇入过大说明该模块被广泛依赖，修改时需要更严格的回归测试。

### 设计原则

概要设计阶段通常遵循以下原则：

1. 模块职责单一，名称能够准确反映功能；
2. 模块之间尽量通过参数传递数据，减少全局状态；
3. 公共功能提取为独立模块，避免重复实现；
4. 接口保持稳定，内部实现可以替换；
5. 控制信息与数据信息分离，避免用标志参数改变模块行为。

## 详细设计

详细设计确定每个模块的内部实现方案，包括数据结构、算法、控制流程与异常处理。详细设计的成果应当足够具体，使编码人员不需要再次进行结构决策。

### 结构化程序设计

结构化程序设计要求任何程序都由三种基本控制结构组合而成：

- **顺序**：语句按书写顺序依次执行；
- **选择**：根据条件执行不同分支；
- **循环**：在条件满足时重复执行一段代码。

结构化程序强调单入口、单出口。每个模块只有一个入口与一个出口，避免随意使用 `goto` 造成控制流跳转混乱。`goto` 在跳出多层循环或统一错误处理时仍有使用价值，但应限制在局部范围内，并明确标注。

### 设计工具

常用的详细设计表达方式包括：

| 工具 | 特点 | 适用场景 |
| :--- | :--- | :--- |
| 流程图 | 直观展示控制流，易于理解 | 算法说明、教学 |
| N-S 图 | 用嵌套方框表示结构，强制结构化 | 详细设计文档 |
| PAD 图 | 用二维图形表示层次与顺序 | 结构化程序设计 |
| 判定表 | 列出条件组合与对应动作 | 复杂条件逻辑 |
| 伪代码 | 接近自然语言，便于转换为代码 | 算法描述 |

判定表适合条件组合较多、分支互相影响的场景。例如成绩等级判定：

| 条件 | 规则 1 | 规则 2 | 规则 3 | 规则 4 |
| :--- | :-: | :-: | :-: | :-: |
| 分数不低于 90 | 是 | 否 | 否 | 否 |
| 分数不低于 80 | 是 | 是 | 否 | 否 |
| 分数不低于 60 | 是 | 是 | 是 | 否 |
| 等级 | 优秀 | 良好 | 及格 | 不及格 |

判定表可以暴露遗漏的条件组合，也便于直接转化为测试用例。

### 数据设计

数据设计确定数据的逻辑结构、存储方式与访问路径。面向过程方法常用结构体组织记录，用数组或链表组织记录集合，用文件或数据库完成持久化。

数据设计需要同时考虑：

- 数据完整性：字段的取值范围与必填约束；
- 访问效率：查询、排序与统计的时间复杂度；
- 存储成本：数据量增长后的空间占用；
- 可扩展性：新增字段时对既有代码的影响。

## 编码实现

编码把详细设计转换为可执行的程序。编码阶段的质量取决于设计质量、编程规范与评审力度。设计缺陷无法通过编码技巧弥补，代码评审首先应检查实现是否符合设计。

### 编码规范

编码规范通常包括：

- 命名：变量、函数、类型使用一致的前缀与大小写约定；
- 注释：说明意图、约束与异常情况，不重复代码字面含义；
- 函数长度：单个函数保持较短，职责单一；
- 参数数量：避免过多参数，必要时使用结构体组织；
- 错误处理：统一返回值约定，检查所有可能失败的操作；
- 资源管理：文件、内存与锁在所有路径上正确释放。

### 代码复杂度

圈复杂度用于衡量函数的判定路径数量。其计算方式为判定节点数加一。复杂度越高，测试所需用例越多，维护难度越大。一般建议单个函数的圈复杂度控制在 10 以内，超过时考虑拆分。

### 完整示例：成绩管理

下面的程序实现需求分析阶段给出的成绩管理功能：从文件读取成绩，校验数据，按分数排序，输出统计报表，并支持按姓名查询。

```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

#define MAX_STUDENTS 100
#define ID_LEN 16
#define NAME_LEN 32

typedef struct {
    char id[ID_LEN];
    char name[NAME_LEN];
    double score;
} Student;

/* 学号按需求定义为 8 位数字 */
static int is_eight_digits(const char *text) {
    if (strlen(text) != 8) {
        return 0;
    }
    for (int i = 0; i < 8; i++) {
        if (text[i] < '0' || text[i] > '9') {
            return 0;
        }
    }
    return 1;
}

/* 读取成绩文件，返回有效记录数；文件无法打开时返回 -1 */
static int read_students(const char *path, Student *students, int capacity) {
    FILE *fp = fopen(path, "r");
    if (fp == NULL) {
        return -1;
    }

    int count = 0;
    char line[128];
    while (count < capacity && fgets(line, sizeof(line), fp) != NULL) {
        Student item;
        if (sscanf(line, "%15s %31s %lf", item.id, item.name, &item.score) == 3
                && is_eight_digits(item.id)
                && item.score >= 0.0 && item.score <= 100.0) {
            students[count++] = item;
        }
    }

    fclose(fp);
    return count;
}

/* 按分数降序排列，分数相同时保持原有相对顺序 */
static int compare_score_desc(const void *left, const void *right) {
    const Student *a = (const Student *) left;
    const Student *b = (const Student *) right;
    if (a->score < b->score) {
        return 1;
    }
    if (a->score > b->score) {
        return -1;
    }
    return 0;
}

static double average_score(const Student *students, int count) {
    double sum = 0.0;
    for (int i = 0; i < count; i++) {
        sum += students[i].score;
    }
    return sum / count;
}

static int count_passed(const Student *students, int count) {
    int passed = 0;
    for (int i = 0; i < count; i++) {
        if (students[i].score >= 60.0) {
            passed++;
        }
    }
    return passed;
}

static int find_by_name(const Student *students, int count, const char *name) {
    for (int i = 0; i < count; i++) {
        if (strcmp(students[i].name, name) == 0) {
            return i;
        }
    }
    return -1;
}

static void print_report(const Student *students, int count) {
    printf("共 %d 名学生\n", count);
    printf("平均分 %.2f\n", average_score(students, count));
    printf("最高分 %.2f（%s）\n", students[0].score, students[0].name);
    printf("最低分 %.2f（%s）\n", students[count - 1].score, students[count - 1].name);
    printf("及格率 %.2f%%\n", 100.0 * count_passed(students, count) / count);

    printf("排名:\n");
    for (int i = 0; i < count; i++) {
        printf("%d. %s %s %.2f\n", i + 1, students[i].id,
               students[i].name, students[i].score);
    }
}

int main(int argc, char *argv[]) {
    if (argc < 2) {
        fprintf(stderr, "用法: %s <成绩文件> [姓名]\n", argv[0]);
        return 1;
    }

    Student students[MAX_STUDENTS];
    int count = read_students(argv[1], students, MAX_STUDENTS);
    if (count < 0) {
        fprintf(stderr, "无法打开文件: %s\n", argv[1]);
        return 1;
    }
    if (count == 0) {
        fprintf(stderr, "文件中没有有效记录\n");
        return 1;
    }

    qsort(students, count, sizeof(Student), compare_score_desc);
    print_report(students, count);

    if (argc >= 3) {
        int index = find_by_name(students, count, argv[2]);
        if (index >= 0) {
            printf("查询结果: %s %s %.2f\n", students[index].id,
                   students[index].name, students[index].score);
        } else {
            printf("未找到学生: %s\n", argv[2]);
        }
    }

    return 0;
}
```

输入文件 `scores.txt`：

```text

20260002 李四 92.0
20260003 王五 58.0
20260004 赵六 76.5
```

编译并运行：

```text

```

1. 20260002 李四 92.00
2. 20260001 张三 87.50
3. 20260004 赵六 76.50

这段代码对应概要设计中的模块划分：`read_students` 负责输入与校验，`qsort` 配合比较函数完成排序，`average_score` 与 `count_passed` 完成统计，`print_report` 负责输出，`find_by_name` 完成查询。每个函数职责单一，模块之间通过参数传递数据，属于数据耦合。

代码中使用了固定大小的数组，最多支持 100 条记录。若数据规模可能超出上限，应改为动态分配或链表，并在读取时检查容量。这一限制在需求分析阶段就应明确，否则会在运行期表现为数据截断。

## 测试

测试的目的是发现缺陷，而不是证明程序没有缺陷。测试只能说明在给定用例下程序行为符合预期，不能穷尽所有输入。

### 测试层次

| 层次 | 对象 | 主要目标 |
| :--- | :--- | :--- |
| 单元测试 | 单个函数、类或模块 | 验证内部逻辑与边界条件 |
| 集成测试 | 模块之间的接口与组合 | 验证数据传递、调用顺序与全局结构 |
| 验收测试 | 用户视角的完整系统 | 验证是否满足业务需求 |
| 平行运行 | 新旧系统同时运行 | 对比结果，降低切换风险 |

### 单元测试

单元测试针对程序的最小可测单元，通常是函数、类或模块。单元测试以白盒方法为主，需要覆盖正常路径、边界条件与异常分支。

单元测试需要测试驱动程序与桩模块。驱动程序模拟调用者，负责传入参数并检查返回值；桩模块模拟被调用模块，返回预设结果。对于成绩管理程序，`read_students`、`average_score`、`count_passed`、`find_by_name` 都可以单独测试。

### 集成测试

集成测试把已测试的模块组合起来，验证模块之间的接口与协作。集成测试分为两个阶段：

- **子系统测试**：把同一子系统内的模块组合起来，重点检查模块间的数据传递、调用顺序与异常传播；
- **系统测试**：把各子系统集成为完整系统，重点检查子系统之间的接口、全局数据结构、性能与兼容性。

模块单独测试通过，不代表组合后没有问题。接口参数含义不一致、全局数据被多个模块修改、异常处理责任不清，都是集成阶段常见的缺陷。

集成策略分为非渐增式与渐增式：

| 策略 | 做法 | 优点 | 缺点 |
| :--- | :--- | :--- | :--- |
| 非渐增式 | 所有模块一次性组装后测试 | 准备工作少 | 缺陷定位困难，接口问题集中爆发 |
| 自顶向下 | 从主控模块开始，逐层加入下层模块，用桩模块代替未完成部分 | 早期验证控制流与主流程 | 底层模块测试较晚，桩模块开发量大 |
| 自底向上 | 从底层模块开始，逐层加入上层模块，用驱动程序调用 | 底层模块尽早验证，不需要桩模块 | 主控逻辑验证较晚，驱动程序开发量大 |
| 混合式 | 上层自顶向下，下层自底向上，在中层汇合 | 兼顾两端，减少桩与驱动 | 汇合点需要规划 |

自顶向下适合控制结构清晰、主流程重要的系统；自底向上适合底层算法复杂、被多处复用的系统；混合式适合层次较多的大型系统。

### 验收测试

验收测试由用户或客户主导，依据需求规格与合同条款验证系统是否可接受。验收测试通常在实际或接近实际的环境中进行，覆盖主要业务流程、非功能指标与异常场景。

常见形式包括：

- **Alpha 测试**：在开发方现场进行，由内部用户或测试人员模拟真实使用；
- **Beta 测试**：在用户现场进行，由真实用户试用并反馈问题；
- **用户验收测试**：按预先定义的验收标准逐项确认。

验收测试通过后，系统进入交付与运行阶段。验收标准应在需求阶段明确，避免在交付前临时增加无法验证的要求。

### 平行运行测试

平行运行测试让新旧系统在一段时间内同时处理相同业务，对比两者的输出与运行指标，确认新系统结果正确后再停用旧系统。

平行运行的优点是风险低，能够在真实数据上验证结果；缺点是需要维护两套系统，数据同步与人工核对成本较高。对账务、计费、库存等结果敏感的系统，平行运行是常用的切换方式。

### 黑盒测试

黑盒测试只依据需求与接口，不关心内部实现。常用方法包括：

- **等价类划分**：把输入划分为有效等价类与无效等价类，每类选取代表性数据。
- **边界值分析**：重点测试取值范围的边界，例如 0、100、-1、101。
- **判定表测试**：为每种条件组合设计用例。
- **因果图**：分析输入条件与输出结果之间的逻辑关系，导出判定表。
- **错误推测**：根据经验推测容易出错的输入，例如空文件、超长姓名、格式错误的行。

### 白盒测试技术

白盒测试依据程序内部结构设计用例，目标是覆盖语句、分支与路径。常用逻辑覆盖标准如下：

| 覆盖标准 | 要求 |
| :--- | :--- |
| 语句覆盖 | 每条可执行语句至少执行一次 |
| 判定覆盖 | 每个判定的真、假分支至少执行一次 |
| 条件覆盖 | 每个判定中的每个条件至少取一次真值与假值 |
| 判定条件覆盖 | 同时满足判定覆盖与条件覆盖 |
| 条件组合覆盖 | 每个判定中所有条件的可能组合至少出现一次 |
| 路径覆盖 | 覆盖所有可能的执行路径 |

以如下片段为例：

```c
if (a > 0 && b > 0) {
    x = 1;
} else {
    x = 0;
}
```

| 用例 | a | b | a > 0 | b > 0 | 判定 | 覆盖效果 |
| :--- | :-: | :-: | :-: | :-: | :-: | :--- |
| T1 | 1 | 1 | 真 | 真 | 真 | 语句、判定、条件组合 |
| T2 | -1 | 1 | 假 | 真 | 假 | 判定、条件组合 |
| T3 | 1 | -1 | 真 | 假 | 假 | 条件、条件组合 |
| T4 | -1 | -1 | 假 | 假 | 假 | 条件组合 |

T1 与 T2 即可满足判定覆盖，但条件覆盖要求每个条件都取过真值与假值，因此还需要 T3 或 T4。条件组合覆盖要求四种组合全部出现，需要 T1 至 T4。路径覆盖要求执行所有可能路径，本例包含两条路径，T1 与 T2 即可覆盖。

覆盖率高不代表测试充分。程序可能实现了需求之外的行为，也可能在覆盖到的路径上产生错误结果。测试用例仍需以需求为依据。

### 基本路径测试

基本路径测试由 McCabe 提出，先根据程序流程图构造控制流图，再计算圈复杂度，最后导出独立路径集合。

圈复杂度 $V(G)$ 可以用以下公式计算：

$$V(G) = E - N + 2$$

其中 $E$ 为边数，$N$ 为节点数。也可以按判定节点数 $P$ 计算：

$$V(G) = P + 1$$

圈复杂度等于独立路径的数量，也是达到基本路径覆盖所需的最少测试用例数。以单分支结构为例：

```c
if (a > 0) {
    x = 1;
} else {
    x = 0;
}
```

控制流图包含四个节点与四条边，$V(G)=4-4+2=2$，需要两条独立路径：条件为真与条件为假。复合条件在短路求值时会产生额外分支，计算时应按实际控制流展开。

基本路径测试的步骤为：

1. 根据源代码绘制控制流图；
2. 计算圈复杂度；
3. 确定一组线性无关的基本路径；
4. 为每条路径设计输入数据；
5. 执行用例并核对结果。

循环结构会显著增加路径数量。对循环应单独设计零次、一次、多次与边界次数用例，避免路径数量爆炸。

### 测试用例设计

针对成绩管理程序，可以设计如下用例：

| 编号 | 输入 | 预期结果 |
| :--- | :--- | :--- |
| T01 | 4 条合法记录 | 输出平均分、最高分、最低分、及格率与排名 |
| T02 | 空文件 | 提示文件没有有效记录，返回非零状态 |
| T03 | 文件不存在 | 提示无法打开文件，返回非零状态 |
| T04 | 分数为 0 与 100 | 两条记录均被接受，边界值正确 |
| T05 | 分数为 -1 与 101 | 两条记录被拒绝 |
| T06 | 学号为 7 位或包含字母 | 该记录被拒绝 |
| T07 | 姓名超过 31 个字符 | 按格式读取失败，该行被跳过 |
| T08 | 查询存在的姓名 | 输出对应学号、姓名与分数 |
| T09 | 查询不存在的姓名 | 输出未找到提示 |
| T10 | 记录数超过 100 | 只读取前 100 条，程序不越界 |

测试执行后应记录实际结果、环境与缺陷编号。缺陷修复后需要执行回归测试，确认修改没有破坏既有功能。

### 缺陷管理

缺陷从发现到关闭通常经历新建、确认、分配、修复、验证、关闭六个状态。每条缺陷应记录复现步骤、预期结果、实际结果、严重程度与影响范围。严重程度与优先级是两个维度：严重程度描述影响，优先级描述修复顺序。

## 运行与维护

软件交付后进入运行与维护阶段。维护不是简单的修错，而是软件生命周期中持续时间最长、成本占比最高的阶段。维护工作包括部署、监控、故障处理、功能调整与性能优化。

### 维护的类型

| 类型 | 目的 | 示例 |
| :--- | :--- | :--- |
| 改正性维护 | 修复运行中发现的缺陷 | 修复统计结果在空输入下的除零错误 |
| 适应性维护 | 适应外部环境变化 | 适配新的操作系统、数据库版本或文件格式 |
| 完善性维护 | 增加功能或改善性能 | 增加按班级统计、优化查询响应时间 |
| 预防性维护 | 提前改善可维护性 | 重构复杂函数、补充自动化测试 |

完善性维护通常占比最高，因为用户需求会随业务发展持续变化。把维护视为二次开发，而不是临时补丁，才能避免系统结构逐步劣化。

### 维护流程

维护请求应先进入变更管理，而不是直接修改生产代码。典型流程为：

1. 提交变更请求，说明问题、影响范围与期望结果；
2. 评估技术方案、工作量与风险；
3. 在独立分支完成修改，并补充或更新测试用例；
4. 执行回归测试，确认既有功能未受影响；
5. 评审通过后发布，记录版本变更与回滚方案；
6. 观察运行指标，确认问题解决且没有引入新问题。

缺少变更控制的维护会导致版本混乱：同一缺陷在不同环境中被反复修复，生产版本与代码仓库不一致，回滚时无法确定应该恢复到哪个状态。

### 可维护性设计

可维护性在设计与编码阶段就已经决定，交付后很难通过维护工作弥补。提高可维护性的措施包括：

- 模块边界清晰，修改影响范围可预测；
- 文档与代码同步，关键决策记录原因；
- 日志包含足够的上下文，便于定位问题；
- 配置与代码分离，环境差异不需要修改源码；
- 自动化测试覆盖核心路径，支持安全重构。

## 生命周期模型

生命周期模型规定阶段的组织方式、迭代节奏与交付方式。不同模型对需求稳定性、风险控制与文档完备性的要求不同，选择模型需要结合项目特征，而不是追随流行做法。

### 瀑布模型

瀑布模型把生命周期划分为需求、设计、编码、测试、维护等阶段，阶段按顺序推进，前一阶段的文档经过评审后作为下一阶段的输入。每个阶段设置里程碑，形成明确的进度控制点。

瀑布模型的优点是结构清晰、文档完备、便于合同管理与进度跟踪。缺点是反馈滞后：用户直到测试阶段才能看到可运行的系统，需求错误发现得越晚，返工成本越高。需求稳定、技术成熟、外部约束严格的项目适合采用瀑布模型。

### 快速原型模型

快速原型模型在正式开发之前构建一个可运行的原型，让用户尽早看到界面与主要流程，从而澄清需求。原型分为抛弃型与演化型：抛弃型只用于需求确认，确认后重新开发；演化型在原型的基础上逐步完善，最终成为产品。

原型的价值在于把抽象需求转化为可讨论的具体对象，降低需求理解偏差。风险在于原型可能被误认为最终产品，导致质量、性能与文档被忽视；演化型原型如果没有良好的结构设计，容易积累技术债务。需求不清晰、界面交互复杂的项目适合先做原型。

### 增量模型

增量模型把系统按功能切分为多个增量，每个增量都经过完整的开发与测试，形成一个可运行的版本。第一个增量通常实现核心功能，后续增量逐步增加功能。

增量模型的优点是能够分批交付、尽早获得反馈，增量之间可以并行开发。缺点是对整体架构要求较高：如果前期没有规划好公共接口与数据模型，后续增量难以集成。功能可以切分、可以分期上线的系统适合增量模型。

### 螺旋模型

螺旋模型由 Boehm 于 1988 年提出，把瀑布模型与原型模型结合起来，并以风险分析为核心。每一轮螺旋包含四个象限：

1. **制定计划**：确定本轮目标、约束与候选方案；
2. **风险分析**：识别风险，构建原型或仿真模型进行验证；
3. **实施工程**：完成本轮的设计、编码与测试；
4. **客户评估**：评审本轮结果，确定下一轮方向。

螺旋模型适合大型、高风险项目，因为每一轮都先处理风险最高的部分。代价是风险分析需要专业能力，管理成本较高；低风险的小型项目采用螺旋模型往往得不偿失。

### 喷泉模型

喷泉模型是面向对象开发常用的生命周期模型。它强调分析、设计、实现与测试之间的连续过渡与反复迭代，阶段之间没有严格边界，就像喷泉的水柱不断上升又回落。

喷泉模型与面向对象方法契合：对象、类与继承关系在分析、设计与实现中保持相同的概念，阶段之间的转换不需要改变模型。优点是支持复用、迭代与渐进式完善；缺点是对项目管理与文档控制要求较高，里程碑不如瀑布模型清晰。采用面向对象方法、需求逐步明确的项目可以使用喷泉模型。

### Rational 统一过程

Rational 统一过程（Rational Unified Process，RUP）是以用例驱动、以架构为中心、迭代且增量的软件开发过程。它把生命周期划分为四个阶段：

| 阶段 | 主要目标 | 里程碑 |
| :--- | :--- | :--- |
| 初始阶段 | 确定业务目标、范围与可行性 | 生命周期目标 |
| 细化阶段 | 建立稳定的架构，消除主要风险 | 生命周期架构 |
| 构造阶段 | 完成剩余功能与测试 | 初始运作能力 |
| 移交阶段 | 部署、培训与用户验收 | 产品发布 |

每个阶段包含若干次迭代，每次迭代都覆盖需求、分析、设计、实现与测试等活动。RUP 定义了九个学科：业务建模、需求、分析与设计、实现、测试、部署、配置与变更管理、项目管理、环境。风险集中在细化阶段处理，架构在早期得到验证。

RUP 适合中大型面向对象项目，尤其是需求逐步明确、需要严格控制架构与风险的场景。完整的 RUP 文档与角色定义较重，实际使用时通常会裁剪。

### 敏捷方法与极限编程

敏捷方法强调个体与协作、可工作的软件、客户合作与响应变化。它不规定统一的流程，而是给出一组价值观与原则，由团队选择具体实践。

极限编程（Extreme Programming，XP）是敏捷方法中实践最具体的一种。XP 的核心价值包括沟通、简单、反馈、勇气，后来补充了尊重。常用实践包括：

- **计划游戏**：由客户与开发人员共同确定本次迭代的范围；
- **小版本发布**：短周期交付可运行的版本；
- **简单设计**：只实现当前需要的功能，避免过度设计；
- **测试驱动开发**：先写测试，再写实现，最后重构；
- **重构**：持续改善代码结构，不改变外部行为；
- **结对编程**：两人共同完成同一段代码，一人编写，一人审查；
- **持续集成**：频繁合并代码并运行自动化测试；
- **代码集体所有**：任何成员都可以修改任何代码；
- **现场客户**：客户全程参与，及时确认需求；
- **编码规范**：团队统一命名、格式与注释约定。

XP 适合需求变化快、团队规模较小、客户能够持续参与的项目。它要求团队有较强的自律与工程能力，否则容易退化为缺少设计、缺少文档的短期开发。

### 微软过程

微软过程通常指 Microsoft Solutions Framework（MSF）的过程模型。它把项目划分为五个阶段：

| 阶段 | 主要工作 | 里程碑 |
| :--- | :--- | :--- |
| 愿景阶段 | 明确业务目标、范围与成功标准 | 愿景与范围确认 |
| 计划阶段 | 制定功能、进度、资源与风险计划 | 项目计划确认 |
| 开发阶段 | 完成功能开发与阶段性测试 | 范围完成 |
| 稳定阶段 | 修复缺陷、完善文档、准备发布 | 发布准备就绪 |
| 部署阶段 | 部署、培训与移交 | 部署完成 |

MSF 结合了瀑布模型的阶段控制与螺旋模型的风险管理，强调里程碑评审、团队角色分工与风险管理。它适合产品化程度较高、按版本发布的软件项目。国内教材中的微软过程一般指这一模型，不同版本的阶段名称可能略有差异。

### 模型比较与选择

| 模型 | 需求特点 | 风险控制 | 交付方式 | 适用场景 |
| :--- | :--- | :--- | :--- | :--- |
| 瀑布 | 稳定、明确 | 依赖前期评审 | 一次交付 | 合同项目、稳定需求 |
| 快速原型 | 不清晰 | 早期需求验证 | 原型后正式开发 | 界面与需求探索 |
| 增量 | 可切分 | 分阶段验证 | 多次交付 | 可分期上线 |
| 螺旋 | 高风险 | 每轮风险分析 | 迭代原型 | 大型高风险项目 |
| 喷泉 | 面向对象、逐步明确 | 迭代验证 | 连续迭代 | 面向对象项目 |
| RUP | 逐步明确 | 架构与风险前置 | 迭代增量 | 中大型面向对象项目 |
| XP | 快速变化 | 持续反馈 | 短周期发布 | 小团队、客户可参与 |
| 微软过程 | 产品化 | 里程碑评审 | 按版本发布 | 产品研发 |

模型选择取决于需求稳定性、技术风险、交付节奏与团队能力。需求稳定、验收标准明确的项目适合瀑布模型；需求不清晰时，先用原型澄清；大型项目可以采用增量交付与螺旋式风险验证的组合；面向对象项目可以选择喷泉模型或 RUP；需求变化快、团队较小且客户可参与时，可以采用 XP。

无论采用哪种模型，需求确认、设计评审、版本控制、测试与变更管理都不可省略。模型改变的是活动顺序与迭代节奏，不改变工程活动本身。

## 工程管理

### 配置管理

配置管理保证项目在任意时刻都能确定当前版本由哪些文件构成，并能恢复到历史状态。核心活动包括：

- **版本控制**：使用 Git 等工具记录每次修改，提交信息说明变更目的；
- **基线管理**：需求、设计、代码与测试在评审通过后形成基线；
- **变更控制**：变更经过申请、评估、批准与验证；
- **发布管理**：记录每个发布版本包含的变更、依赖与回滚方案。

Git 的常用实践包括主干开发或分支开发、提交前本地检查、合并请求评审、标签标记发布版本。分支策略应服务于团队规模与发布频率，不必照搬特定流程。

### 质量保证

质量保证关注过程是否按规范执行，质量控制关注产品是否满足要求。二者的区别在于前者面向过程，后者面向结果。

常用质量活动包括：

- 需求评审、设计评审与代码评审；
- 静态分析，检查空指针、越界、未初始化变量与资源泄漏；
- 单元测试、集成测试与回归测试；
- 缺陷跟踪与趋势分析；
- 发布前的检查清单与签署确认。

代码评审应聚焦正确性、边界条件、错误处理与可维护性，而不是格式偏好。格式问题应交给自动化工具处理。

### 度量

度量用于判断过程是否稳定、质量是否改善。常用指标包括：

| 指标 | 含义 | 用途 |
| :--- | :--- | :--- |
| 代码规模 | 有效代码行数或功能点 | 估算工作量与维护成本 |
| 缺陷密度 | 每千行代码的缺陷数 | 评估模块质量与测试充分性 |
| 缺陷逃逸率 | 发布后发现的缺陷占全部缺陷的比例 | 评估测试有效性 |
| 需求变更率 | 变更需求占总需求的比例 | 评估需求稳定性 |
| 进度偏差 | 实际进度与计划进度的差异 | 评估计划准确性 |
| 平均修复时间 | 缺陷从确认到关闭的平均耗时 | 评估维护效率 |

度量指标容易被误用。把代码行数作为绩效指标会鼓励冗余代码，把缺陷数作为唯一质量指标会抑制缺陷报告。度量应服务于过程改进，而不是用于个体排名。

### 风险管理

风险是尚未发生但可能影响项目目标的事件。风险管理包括识别、评估、应对与监控：

- **识别**：技术风险、需求风险、人员风险、进度风险、外部依赖风险；
- **评估**：估计发生概率与影响程度，确定优先级；
- **应对**：规避、转移、减轻或接受；
- **监控**：定期复查风险状态，触发预案。

高风险项应有明确的验证手段。例如关键技术未经验证时，先做原型或技术验证，而不是在项目后期才发现方案不可行。

### 成熟度模型

CMMI 把组织的过程能力划分为五个等级：

| 等级 | 名称 | 特征 |
| :--- | :--- | :--- |
| 1 | 初始级 | 过程依赖个人经验，结果难以预测 |
| 2 | 已管理级 | 项目级过程受控，有基本的计划与跟踪 |
| 3 | 已定义级 | 组织级标准过程建立，项目按裁剪后的标准执行 |
| 4 | 定量管理级 | 使用统计方法对过程与质量进行定量控制 |
| 5 | 优化级 | 基于度量持续改进过程 |

ISO/IEC 12207 则从过程角度定义软件生命周期的活动，包括获取、供应、开发、运行、维护与支持过程。这些标准提供的是框架，落地时需要结合组织规模与项目特点裁剪。

## 面向过程与面向对象的取舍

面向过程方法以功能与数据流为中心，适合计算密集、流程清晰、数据结构相对稳定的系统。操作系统内核、嵌入式控制、科学计算与数据处理工具大量采用这一范式。C 语言的生态与这类场景高度契合。

面向对象方法以对象与职责为中心，适合业务规则复杂、类型层次丰富、需要长期演进的系统。图形界面、企业应用与领域模型通常更适合面向对象。

两种方法并非互斥。面向对象系统内部仍需要过程式的算法实现，面向过程系统也可以使用封装与模块化思想。选择方法时应考虑：

- 问题的主要复杂性来自流程还是来自类型与状态；
- 需求变化的常见方向是新增流程还是新增类型；
- 团队熟悉的语言与工具链；
- 系统规模与预期生命周期。

无论采用哪种范式，软件工程的基本要求不变：需求可追踪、设计可评审、代码可维护、测试可重复、变更可控制。

## 面向对象方法简介

面向对象方法把对象作为系统的基本构造单元。对象封装状态与行为，类描述同一类对象的共性，继承组织类型层次，多态支持同一接口的不同实现。面向对象开发通常分为三个阶段：

- **面向对象分析（OOA）**：从问题域中识别对象、类、属性、操作与关系，建立领域模型；
- **面向对象设计（OOD）**：确定系统架构、类结构、接口与交互，补充实现约束；
- **面向对象编程（OOP）**：用具体语言实现类与对象，完成测试与集成。

面向对象方法强调用例驱动、以架构为中心、迭代增量。统一建模语言（UML）提供用例图、类图、对象图、时序图、活动图、状态图等表达方式，用于描述需求、结构与交互。RUP 是面向对象过程的典型代表，喷泉模型则强调分析、设计与实现之间的连续过渡。

与面向过程方法相比，结构化方法以功能与数据流为中心，适合流程稳定、计算密集的系统；面向对象方法以对象与职责为中心，适合业务规则复杂、类型层次丰富、需求持续变化的系统。两种方法可以结合使用：总体结构采用面向对象设计，具体算法仍以过程式代码实现。

## 结语

面向过程的软件生命周期以阶段划分为骨架，以文档与评审为控制点，以模块化与结构化设计为方法核心。可行性研究决定是否投入，需求分析确定系统边界，概要设计建立模块结构，详细设计确定算法与数据，编码把设计转化为程序，测试验证行为，维护承担长期演进。

生命周期模型改变活动的组织方式，但不替代工程活动本身。瀑布、原型、增量、螺旋、迭代与敏捷各有适用条件，选择依据是需求稳定性、技术风险与交付节奏。

软件工程的最终目标是让软件在可预期的成本内持续满足需求。实现这一目标依靠的是可重复的过程、清晰的文档、受控的变更与充分的验证，而不是依赖个别开发者的经验。
