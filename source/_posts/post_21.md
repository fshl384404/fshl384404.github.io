## 型号命名的读法

大模型厂商用不同的名字区分同一代基座下的多个型号。名字本身没有统一含义，同一个词在不同厂商那里可能对应完全不同的定位。选型时先看厂商对型号的定义，再比较差异，不能把一家的命名规则套到另一家。

当前主流厂商的命名大致沿四个方向分化：

| 分化方向 | 常见表现 | 典型例子 |
| :--- | :--- | :--- |
| 能力档位 | 旗舰、主力、轻量 | GPT-6 Astra、Sol、Terra、Luna |
| 任务专长 | 编程、知识工作、网络安全 | Gemini 4 Argon、Carbon、Neon |
| 延迟与吞吐 | 标准版、快速版、极速版 | GLM-5.3、Flash、FlashX |
| 模态 | 文本、全模态、图像、语音 | Qwen4-Max、Qwen3.8-Omni-Flash |

版本号与型号名是两套信息。版本号表示基座或后训练的更新，型号名表示产品定位。选型主要看型号定位，版本号用于确认当前可用的具体版本。下面按厂商说明当前型号的差异，不讨论代际演进。

## OpenAI GPT-6

### 四款型号

GPT-6 当前有四款型号，分别覆盖攻坚、专业开发、日常主力与快速批量四类任务。

| 型号 | 定位 | 适用任务 |
| :--- | :--- | :--- |
| Astra | 攻坚旗舰 | 最复杂的推理、长时程 Agent、失败代价极高的任务 |
| Sol | 专业开发 | 复杂编程、生产级 Agent、深度分析 |
| Terra | 日常主力 | 通用办公、写作、分析、日常开发 |
| Luna | 快速批量 | 分类、抽取、路由、结构化摘要、高吞吐任务 |

### 差异

Astra 的差异在推理深度与自主性。它适合需要多步规划、跨工具协作、长时间无人监督运行的任务。失败代价高、需要尽量减少人工介入的场景，优先选择 Astra。

Sol 的差异在专业开发能力与延迟的平衡。它的编程与 Agent 能力接近旗舰，但响应更快，适合日常的复杂开发任务。对多数工程团队，Sol 是生产环境的起点。

Terra 的差异在通用性。它覆盖写作、分析、办公与一般开发，能力低于 Astra 与 Sol，但延迟与成本更适合日常高频使用。Terra 适合作为默认入口。

Luna 的差异在速度与吞吐。它面向边界清晰、可规模化重复的任务，例如字段抽取、请求分类、内容摘要与路由。任务验收标准越明确，Luna 的单位成本优势越明显。

### 型号分工

四款型号把任务难度与延迟要求映射到四个档位。Astra 承担最高推理预算与长时程 Agent；Sol 降低延迟但保留专业开发能力；Terra 覆盖通用日常任务；Luna 通过蒸馏与推理优化覆盖高吞吐。共享基座使 OpenAI 能用一套模型覆盖从批量抽取到攻坚的任务区间，代价是路由与版本策略不透明。

### 技术路线

OpenAI 未公开 GPT-6 的参数量、注意力结构与训练数据规模。从产品行为与公开材料可以确认三个方向：统一模型与路由、推理时计算扩展、Agent 工具使用。

统一模型把对话、推理、编程与多模态输入放在同一基座。路由根据任务难度选择推理预算，简单任务走低预算路径，复杂任务分配更多思考 token。Agent 能力来自工具调用、计算机操作与长时程任务的后训练，模型需要在多轮交互中保持目标、处理失败并恢复状态。

Astra 与 Luna 的差异不仅来自参数规模，还包括推理预算、后训练数据与推理优化。Astra 使用更高的推理预算与更强的 Agent 后训练，Luna 通过蒸馏与推理优化换取速度。四款型号共享基座，使 OpenAI 可以用一套模型覆盖从批量抽取到长时程攻坚的任务区间。

局限在于闭源与不透明。路由策略、推理预算与版本差异不对外公开，调用方难以精确预测成本与延迟；版本更新频繁，生产系统需要锁定版本并持续回归测试。

## Google Gemini

### 四款型号

Gemini 4 当前有四款型号：Argon、Carbon、Neon、Hydrogen。四者按任务专长与效率分工，能力大小不是唯一的排序依据。

| 型号 | 定位 | 适用任务 |
| :--- | :--- | :--- |
| Argon | 前沿旗舰 | 复杂软件工程、企业知识工作、网络安全 |
| Carbon | 前沿长时程 Agent | 长时程知识工作、研究、企业流程 |
| Neon | 高性能快速旗舰 | 编程、多步推理、企业 Agent 工作流 |
| Hydrogen | 高效通用 | 日常任务、广泛用户访问、速度优先 |

### 差异

Argon 的定位是前沿能力加专业场景。Google 对它的说明强调真实软件工程、企业知识工作与网络防御，适合需要最高能力且任务领域明确的场景。

Carbon 的定位是长时程 Agent。它在复杂知识工作中保持多步规划与上下文连续性，适合研究、企业流程与需要长时间运行的任务。Argon 与 Carbon 都属于前沿型号，差异在任务侧重：Argon 偏工程与安全，Carbon 偏知识工作与长时程。

Neon 的定位是快速前沿。它面向高性能编码、多步推理与企业 Agent 工作流，强调端到端任务的快速完成。Neon 的能力接近前沿，但延迟低于 Argon 与 Carbon。

Hydrogen 的定位是效率与普及。它强调速度与执行效率，面向所有用户的日常任务。Hydrogen 不适合最复杂的推理，但在响应速度与可用性上占优。

### 型号分工

Argon 与 Carbon 都属前沿型号，前者偏工程与安全，后者偏长时程知识工作；Neon 提供快速前沿，Hydrogen 提供高效普及。分层让 Google 在同一代多模态基座上覆盖深度、速度与成本三个方向。

### 技术路线

Gemini 4 的核心是原生多模态与长上下文。文本、图像、音频与视频在同一表示空间中编码，模型可以跨模态对齐，而不是由多个专用模型拼接。长上下文依赖高效注意力机制与大规模 TPU 集群，训练与推理成本都很高。

四款型号的分工体现了 Google 对场景的划分。Argon 面向真实软件工程、企业知识工作与网络防御；Carbon 面向长时程知识工作与研究；Neon 提供快速前沿能力，适合编程与多步推理；Hydrogen 强调速度与执行效率，面向广泛用户。Argon 与 Carbon 属于前沿型号，Neon 是快速前沿，Hydrogen 是高效档位。

多模态与长上下文带来三类工程问题：模态 token 化与对齐、长序列注意力的计算与显存开销、跨模态 grounding 与安全。Google 通过 TPU 集群、分层模型与产品侧工具调用缓解这些问题，但模型能力与 Google 生态高度耦合，跨平台可用性受产品策略影响。

## Anthropic Claude

### 四个家族

Claude 当前分为 Mythos（含 Fable）、Opus、Sonnet、Haiku 四个家族。

| 家族 | 定位 | 适用任务 |
| :--- | :--- | :--- |
| Mythos / Fable | 顶层长时程 Agent | 跨系统编排、多步规划、长时间自主运行 |
| Opus | 深度推理与复杂编码 | 架构设计、难缺陷定位、高可靠企业任务 |
| Sonnet | 通用主力 | 日常编程、写作、分析、生产环境默认 |
| Haiku | 低延迟轻量 | 实时对话、分类、路由、结构化抽取 |

### 差异

Fable 的差异在任务时程。它面向需要持续数小时、跨多个系统与工具的任务，强调目标保持、状态记录与失败恢复。单轮回答质量不是它的主要区别。

Opus 的差异在推理深度。它适合复杂编码、架构设计与需要高可靠性的企业任务。与 Fable 相比，Opus 更偏向单次任务的深度，而不是长时间自主运行。

Sonnet 的差异在平衡。它的能力覆盖日常编程与知识工作，延迟与成本适合生产环境。多数团队可以从 Sonnet 开始，遇到能力瓶颈再向上选择 Opus 或 Fable，向下选择 Haiku。

Haiku 的差异在速度。它适合实时对话、分类、路由与结构化抽取，不适合多步规划或需要综合长上下文的任务。

### 型号分工

四个家族按任务时程与延迟分工。Haiku 处理短时任务，Sonnet 承担日常生产，Opus 处理深度推理，Fable 处理长时程 Agent。共享训练体系使能力沿家族递进，差异主要在推理预算、后训练与推理优化。

### 技术路线

Claude 的训练强调 Constitutional AI 与人类反馈的结合。Constitutional AI 用一组明确原则约束模型行为，减少对大量人工标注的依赖；偏好优化调整回答的有用性、诚实性与无害性。Anthropic 同时投入可解释性研究，试图理解模型内部特征与行为。

长时程 Agent 是 Claude 的重点。Fable 面向持续数小时、跨多个系统与工具的任务，难点不在单轮推理，而在复合误差、状态跟踪与工具失败恢复。多轮任务中，前一步的小错误会沿工具调用链放大，模型需要记录中间状态、验证结果并在失败时回退。评估这类能力需要轨迹级指标，单轮基准无法反映真实表现。

局限在于保守倾向与闭源。安全对齐会降低模型在边界场景中的冒险程度，某些高自主性任务需要额外提示与工具支持；权重不可用，私有化与深度定制受限。

## DeepSeek

### 当前型号

DeepSeek 当前提供两款主要型号：V4.1-Flash 与 V4-Pro。

| 型号 | 定位 | 适用任务 |
| :--- | :--- | :--- |
| DeepSeek-V4.1-Flash | 当前主力 | 原生多模态、通用任务、高吞吐调用 |
| DeepSeek-V4-Pro | 旗舰 | 复杂推理、高难度工程、深度分析 |

### 差异

V4.1-Flash 的差异在效率与多模态。它在 Flash 档位上加入原生多模态输入，适合图文理解、文档处理与高频调用。V4.1-Flash 是当前 Flash 档位的正式型号，承担高吞吐与多模态任务。

V4-Pro 的差异在能力上限。它拥有约 1.6T 总参数，面向复杂推理与高难度任务。V4-Pro 的响应更慢、成本更高，适合失败代价高、需要更深推理的场景。

### 型号分工

两款型号的分工直接：V4-Pro 承担质量上限与复杂推理，V4.1-Flash 承担规模化调用与多模态任务。思考模式作为运行时开关存在，使同一个模型可以在普通回答与深度思考之间切换。

### 技术路线

DeepSeek 的架构以参数效率为核心。MoE 把总参数与激活参数分离，推理时只激活部分专家；MLA 注意力通过低秩投影压缩键值缓存，降低长上下文推理的显存占用。V3 采用 671B 总参数、约 37B 激活参数，验证了大规模 MoE 的可行性。

R1 的训练路线包括冷启动监督微调、面向可验证任务的强化学习、拒绝采样与再训练。数学与代码等任务有明确判定标准，可以用规则奖励替代人类偏好模型，降低标注成本。V4-Pro 把总参数扩大到约 1.6T，面向复杂推理；V4.1-Flash 在 Flash 档位加入原生多模态，承担高吞吐与图文任务。

DeepSeek 的设计取舍是效率优先与开放权重。开放权重使模型可以被本地部署、微调与蒸馏，开放权重型号与 API 旗舰的能力边界需要分别核对。长上下文与多模态的工程成熟度仍需要按具体任务验证。

## 智谱 GLM

### 当前型号

智谱当前的主力是 GLM-5.3 系列，另有 GLM-5.2 作为同基座的稳定版本。

| 型号 | 定位 | 适用任务 |
| :--- | :--- | :--- |
| GLM-5.3 | 旗舰 | 复杂软件工程、Agent、长上下文 |
| GLM-5.3-Flash | 多模态主力 | 原生多模态，质量与成本平衡 |
| GLM-5.3-FlashX | 高速版本 | 低延迟、高吞吐，输出速度约 200 tokens/s |
| GLM-5.2 | 稳定版本 | 与 5.3 同基座，适合稳定性优先的场景 |

### 差异

GLM-5.3 的差异在软件工程与 Agent 能力。它支持 1M 上下文，适合代码库分析、长文档处理与多轮工具调用。GLM-5.3 与 GLM-5.2 使用相同的基础模型，差异来自后训练与思考模式。

GLM-5.3-Flash 的差异在原生多模态。它是该系列首个原生多模态版本，适合图文理解、文档识别与多模态 Agent。

GLM-5.3-FlashX 的差异在速度。它面向低延迟与高吞吐场景，输出速度可达约 200 tokens/s，适合实时交互与批量处理。

GLM-5.2 的差异在稳定性。它与 5.3 共享基座，适合不希望频繁跟随新版本的用户。

### 型号分工

GLM-5.3、5.3-Flash、FlashX 与 5.2 共享基座，通过后训练、模态扩展与推理优化形成旗舰、多模态、高速与稳定四个版本。共享基座降低训练成本，代价是型号命名密集。

### 技术路线

GLM 系列起源于自回归空白填充的训练目标，后在 MoE 架构上扩展。GLM-5 采用约 745B 总参数、44B 激活参数的 MoE，上下文约 200K；GLM-5.3 与 GLM-5.2 共享基础模型，通过后训练与思考模式形成差异，上下文扩展到 1M。

GLM-5.3 的后训练重点在软件工程与 Agent 任务，训练数据包含代码、工具调用与多轮任务轨迹。GLM-5.3-Flash 是该系列首个原生多模态版本，覆盖图文理解与文档识别；FlashX 通过推理优化把输出速度提升到约 200 tokens/s。

智谱的策略是同一基座的多形态复用与开源闭源并行。共享基座降低训练成本，后训练与推理优化形成旗舰、多模态、高速与稳定四个版本。代价是型号命名密集，调用方需要区分基座代际、后训练版本与推理档位。

## Moonshot Kimi

### 当前型号

Kimi 当前的主力是 K3.1 Pro，上一代旗舰为 K3。

| 型号 | 定位 | 适用任务 |
| :--- | :--- | :--- |
| K3.1 Pro | 当前旗舰 | 复杂编程、Agent、深度研究、3D 与金融分析 |
| K3 | 上一代旗舰 | 长上下文任务，稳定性优先 |

### 差异

K3.1 Pro 的差异在编程与 Agent 能力。它的公开说明强调复杂编程项目、3D 模型构建与金融研究，这些任务依赖长上下文、工具调用与多步规划。

K3 的差异在架构。K3 拥有约 2.8 万亿参数，采用 KDA 混合线性注意力（Kimi Delta Attention），在长上下文场景中降低注意力计算随长度增长的成本。K3.1 Pro 在此基础上强化后训练与 Agent 能力。

### 型号分工

K3.1 Pro 承担当前旗舰，K3 继续服务稳定性要求较高的场景。Kimi 的型号数量较少，产品重点集中在长上下文、编程与 Agent，而不是覆盖所有模态与价位。

### 技术路线

Kimi 的技术路线以长上下文效率为核心。K3 拥有约 2.8 万亿参数，采用 KDA 混合线性注意力（Kimi Delta Attention）。标准注意力的计算与显存随序列长度平方增长，KDA 把部分注意力层替换为线性注意力，在保留局部精确注意力的同时降低全局计算成本。

K3.1 Pro 在 K3 的基础上强化后训练与 Agent 能力，重点覆盖复杂编程、3D 建模与金融研究。这些任务共同依赖长上下文理解、工具调用与多步规划。长上下文能力不仅来自窗口大小，还依赖训练数据中的长文档、代码库与多轮轨迹。

局限在于模态与生态。Kimi 的强项集中在文本、代码与 Agent，图像、视频与语音主要依赖专用接口或合作模型；生态规模相对有限，第三方工具与微调资源不如头部开源系列丰富。

## xAI Grok

### 当前分线

Grok 当前主线为 Grok 4 系列，产品线按推理与非推理分为两类。

| 类型 | 定位 | 适用任务 |
| :--- | :--- | :--- |
| 推理型号 | 深度思考、复杂问题求解 | 多步推理、代码、研究型任务 |
| 非推理型号 | 低延迟、日常对话 | 问答、摘要、一般写作 |

### 差异

推理型号的差异在思考深度。它在回答前进行多步推理，适合复杂问题、代码与研究任务，代价是延迟更高。

非推理型号的差异在速度。它不进行显式长链思考，适合日常问答与一般任务，响应更快。

xAI 的版本命名不完全遵循递增规则，同一代际内会出现多种后缀。选型时应以官方文档中的能力说明为准，不能仅凭版本号判断强弱。

### 型号分工

Grok 按推理与非推理分线。推理型号承担复杂问题与研究型任务，非推理型号承担日常问答与高吞吐。xAI 的版本命名不完全遵循递增规则，选型应以官方说明为准。

### 技术路线

Grok 的差异化来自实时信息与强化学习。模型与 X 平台的数据流集成，可以访问实时帖子、趋势与公共讨论；训练侧强调大规模强化学习与推理能力，产品侧强调直接的回答风格与较少的产品限制。

推理型号在回答前进行多步思考，适合复杂问题、代码与研究任务；非推理型号不进行显式长链思考，适合日常问答与高吞吐场景。xAI 还提供多智能体协作，让多个模型实例分工完成研究、验证与写作。

局限在于数据质量与版本稳定性。社交媒体数据包含错误信息、重复内容与情绪化表达，实时检索需要额外的来源校验；版本命名不完全遵循递增规则，生产系统需要锁定版本并做回归测试。

## 阿里 Qwen

### 当前型号

Qwen4-Max 的差异在旗舰全模态。它融合文本生成、图片与视频理解、深度思考与编程能力，适合重度 Agent 与复杂多模态任务。

Qwen3.8-Omni-Flash 的差异在全模态。它在轻量档位上统一处理文本、图像、音频与视频，适合多模态交互与实时应用。

### 型号分工

Qwen4-Max 承担旗舰全模态，3.7-Plus 承担质量与成本平衡，3.8-Flash 承担高吞吐，Omni-Flash 承担轻量全模态。专用模型覆盖图像、视频与语音，形成从端侧到云端的完整阶梯。

### 技术路线

Qwen 的路线是尺寸阶梯、开放权重与多模态覆盖。Qwen4-Max 是旗舰全模态模型，融合文本生成、图片与视频理解、深度思考与编程；Qwen3.7-Plus 承担质量与成本平衡；Qwen3.8-Flash 面向高吞吐；Qwen3.8-Omni-Flash 在轻量档位统一处理文本、图像、音频与视频。

专用模型覆盖生成与语音：Qwen-Image 3.0 负责图像生成与编辑，Wan 3.0 负责视频生成，Qwen-Audio 3.1 覆盖 ASR、TTS 与实时对话。训练数据强调中文、多语言、代码与 Agent 轨迹，API 接口保持与 OpenAI 兼容，降低迁移成本。

开放权重是 Qwen 的重要差异。部分型号允许本地部署、微调与蒸馏，使 Qwen 成为开源社区的重要基座；旗舰型号通过云平台提供，承担最高能力与多模态任务。代价是型号数量多、版本关系复杂，选型需要仔细核对定位。

## 架构与训练的共性取舍

### 稠密模型与 MoE

稠密模型每次推理激活全部参数，行为稳定、实现简单，但推理成本随参数量线性增长。MoE 把参数划分为多个专家，每个 token 只激活少数专家，在总参数扩大的同时控制单次计算量。DeepSeek、GLM 与 Kimi 都采用 MoE 或混合结构。

MoE 的代价是训练与 serving 复杂度。路由需要负载均衡，避免少数专家过载；专家并行会增加通信开销；微调时容易出现专家退化。MoE 的总参数不能直接等同于能力，激活参数、专家数量与训练数据共同决定表现。

### 注意力与长上下文

标准全注意力在长序列上计算与显存开销高。长上下文模型采用稀疏注意力、线性注意力或混合结构。Kimi 的 KDA 把全注意力与线性注意力结合，DeepSeek 的 MLA 压缩键值缓存，Gemini 与 Claude 通过工程优化扩展上下文。

长上下文的能力不只取决于窗口大小。检索精度、位置外推、长文档训练数据与中间信息保持都会影响实际表现。评估时应使用长文档问答、代码库理解与多轮任务，而不是只看最大 token 数。

### 原生多模态与适配器

原生多模态在预训练阶段就把不同模态映射到统一表示，跨模态对齐更充分；适配器方案在已有语言模型上增加视觉或音频编码器，成本低但模态融合较浅。Gemini 与 Qwen Omni 强调原生多模态，Claude 与 GPT 的多模态能力覆盖图像输入与工具调用，图像、视频与语音生成通常由专用模型承担。

多模态理解与多模态生成是两条不同的技术路线。理解任务依赖编码与对齐，生成任务依赖扩散或自回归解码。图像、视频与语音模型通常独立演进，再通过统一接口与语言模型组合。

### 后训练与推理预算

后训练包括监督微调、人类反馈强化学习、AI 反馈强化学习与可验证奖励强化学习。数学、代码等有明确判定标准的任务适合规则奖励；写作、对话与安全行为更适合人类或 AI 偏好。

推理预算把后训练能力转化为运行时选项。同一个基座可以通过思考开关、思考长度与路由策略覆盖不同难度任务。预算越高，延迟与成本越高，收益在复杂任务上更明显，在简单任务上可能为负。

### Agent 与评估

Agent 能力依赖工具调用、状态管理、错误恢复与长时程规划。单轮 benchmark 无法衡量这些能力，评估需要多轮任务、工具环境与失败样本。模型在演示任务上的表现，不能直接外推到生产环境。

公开基准存在数据污染与饱和问题。选型应使用自己的任务分布，记录通过率、人工介入率、延迟与成本，并在版本升级后重新测试。

### 长上下文的存储账

长上下文的首要成本是键值缓存。对标准多头注意力，键值缓存的大小为：

$$2 \times L \times H \times D \times S \times B$$

其中 $L$ 为层数，$H$ 为注意力头数，$D$ 为每头维度，$S$ 为序列长度，$B$ 为每个元素的字节数，系数 2 表示键与值各一份。

以 32 层、32 头、每头 128 维、32K 上下文、FP16 存储为例：

$$2 \times 32 \times 32 \times 128 \times 32768 \times 2 \approx 16\text{GiB}$$

单个请求的键值缓存就接近 16 GiB，批量推理的显存压力更大。上下文扩展到 1M 时，标准注意力的缓存无法直接承受。

这解释了三种技术路线。MLA 通过低秩投影压缩键值表示，降低每 token 的缓存占用；线性注意力用固定大小的状态替代随长度增长的缓存；混合结构在局部使用全注意力保证精度，在全局使用线性注意力控制成本。长上下文能力不仅是训练窗口的问题，也是推理显存与带宽的问题。

### MoE 的计算账

MoE 把总参数与激活参数分离。以 671B 总参数、37B 激活参数为例，每个 token 只经过约 5.5% 的参数，单 token 的计算量接近 37B 稠密模型，但显存中需要容纳全部专家。

这带来两个后果。第一，MoE 降低计算成本，但不降低显存占用；专家并行时还需要跨节点通信。第二，批量较小时，路由与通信开销占比上升，MoE 的成本优势可能无法体现。MoE 适合高吞吐、较大批量的服务场景，不适合极低延迟的单请求场景。

### 推理预算的账

推理型模型在回答前生成思考 token。设答案需要 100 个 token，思考需要 1000 个 token，生成成本约为非推理模式的 11 倍，延迟也相应增加。

推理预算的收益取决于任务难度。数学证明、复杂代码与多步规划可以从思考中获益；分类、抽取与简单问答的收益很小，甚至因为过度思考而降低稳定性。按任务难度分配推理预算，比所有请求统一使用最高预算更经济。

### 简要说明

混元的优势在企业集成。腾讯云、微信与企业办公场景为混元提供了落地入口，模型覆盖文本、图像与语音。对已经在腾讯生态内的团队，混元的接入成本较低。

豆包的优势在消费级产品与内容生成。豆包助手覆盖对话、写作与多模态生成，Seedance 2.0 提供视频生成能力。豆包的能力与产品体验绑定较紧，适合内容创作与轻量应用。

文心一言的优势在中文知识与搜索。百度的搜索索引与知识图谱为模型提供外部知识来源，适合问答、百科与行业知识场景。

Step 采用多模态与高效推理路线，Step 5 Preview 面向开发者提供预览能力。Step 的生态规模较小，适合作为特定任务的补充模型。

MiniMax 的产品线覆盖通用模型、语音与视频。M3.1-Flash 面向高吞吐场景，海螺视频在生成质量与运镜控制上有一定特色。

Llama 与 Mistral 代表开放权重路线。Llama 的生态成熟，工具链、微调方法与部署方案丰富；Mistral 强调欧洲合规与私有化部署，模型规模相对克制。两者的能力上限与闭源旗舰存在差距，但权重可控、成本可预测。

RWKV 是一种架构路线，而不是单一模型。它把 Transformer 的并行训练与 RNN 的线性推理结合起来，RWKV-7 Goose 等型号在长上下文与显存效率上有优势。RWKV 的生态规模较小，工具链与预训练资源不如主流 Transformer 模型丰富。

JEV 的定位与通用大模型不同。它面向软件与 Agent 的状态评估，读取程序状态后返回分类、评分或选择，适合作为决策组件嵌入工作流。JEV 不承担开放式生成任务，评估时应按分类准确率与决策一致性衡量。

## 多模态生成模型

### 图像生成

图像生成模型的主流架构是扩散模型与 Diffusion Transformer。文本编码器把提示词转换为条件向量，扩散过程在潜空间中逐步去噪，最终由解码器还原为图像。近年的改进集中在文本对齐、中文排版、图像编辑与多图一致性。

| 模型 | 所属 | 特点 |
| :--- | :--- | :--- |
| Qwen-Image 3.0 | 阿里 | 中文排版与图像编辑，适合海报、电商图 |
| Wan 2.7 Image | 阿里 | 与视频模型同源，风格覆盖广 |
| GLM-Image | 智谱 | 与 GLM 生态集成，适合中文内容 |
| Seedream | 字节跳动 | 生成与编辑统一架构，适合创意设计 |
| GPT Image | OpenAI | 指令遵循与文字渲染较强，适合通用创作 |
| Midjourney | Midjourney | 艺术风格与审美控制见长 |
| FLUX | Black Forest Labs | 开放权重，社区微调生态丰富 |

图像模型的评估应关注提示词遵循、构图、文字渲染、手部与细节、编辑一致性。公开演示图往往经过挑选，实际选型应使用自己的产品图、人物图与中文海报做测试。

### 视频生成

视频生成在图像生成的基础上增加时间维度。模型需要保持帧间一致性、人物身份稳定、镜头运动自然，并处理音频与口型同步。当前路线包括扩散视频模型与自回归视频模型，前者在画质上占优，后者在长视频与交互生成上有潜力。

| 模型 | 所属 | 特点 |
| :--- | :--- | :--- |
| Wan 3.0 | 阿里 | 文生视频、图生视频，生态完整 |
| Kling 3.0 Omni / 4.0 | 快手 | 多模态输入、音画同步、主体一致性 |
| Seedance 2.0 | 字节跳动 | 与豆包集成，面向内容创作 |
| Hailuo | MiniMax | 运镜与画面质感，消费级创作 |
| Veo | Google | 与 Gemini 生态集成，物理一致性 |
| Sora | OpenAI | 长镜头与复杂场景生成 |

视频模型的评估应关注时长、分辨率、帧率、运动自然度、主体一致性、音画同步与可控性。生成成本随时长与分辨率快速上升，实际使用通常采用短片段生成、后期拼接的工作流。

### 语音模型

语音模型分为识别、合成与实时对话三类。识别模型把音频转为文本，合成模型把文本转为语音，实时对话模型直接完成语音到语音的端到端交互。端到端模型的延迟更低，但可控性与可解释性弱于分阶段方案。

| GPT Realtime | OpenAI | 端到端实时语音，适合语音助手 |
| Gemini Live | Google | 与 Gemini 多模态能力集成 |
| MiniMax Speech | MiniMax | 语音合成与克隆，音色丰富 |

语音模型的评估应关注识别准确率、噪声鲁棒性、合成自然度、音色一致性、首包延迟与打断处理。

## 选型方法

型号选择应先确定任务类型与失败代价，再比较同代型号的差异。下表按场景给出起点，不构成固定结论。

| 场景 | 优先候选 | 选择依据 |
| :--- | :--- | :--- |
| 高吞吐分类与抽取 | GPT-6 Luna、Claude Haiku、Gemini 4 Hydrogen、GLM-5.3-FlashX | 任务边界清晰，延迟与吞吐优先 |
| 日常编程与写作 | GPT-6 Terra、Claude Sonnet、Qwen3.7-Plus | 质量与成本平衡 |
| 专业开发与生产级 Agent | GPT-6 Sol、Claude Opus、Gemini 4 Neon | 编程能力与响应速度兼顾 |
| 最复杂推理与攻坚 | GPT-6 Astra、Claude Fable、Gemini 4 Argon | 失败代价高，推理深度与自主性优先 |
| 长时程知识工作 | Gemini 4 Carbon、Claude Fable | 长上下文、多步规划与状态保持 |
| 原生多模态理解 | Gemini 4、Qwen4-Max、Qwen3.8-Omni-Flash | 图文音视频统一处理 |
| 长文档与代码库 | Kimi K3.1 Pro、GLM-5.3、Gemini 4 Carbon | 长上下文与检索精度 |
| 私有化与微调 | Qwen 开放型号、Llama、Mistral、RWKV | 权重可控、部署成本可预测 |

选型的最后一步是用真实失败样本做小规模测试。公开基准衡量平均能力，实际业务关心特定分布上的失败率。测试应记录任务通过率、人工介入率、延迟分布与版本差异，并在型号升级后重新执行。

## 结语

同一代大模型的差异，主要体现在能力档位、任务专长、延迟与模态。Astra 与 Luna、Argon 与 Hydrogen、Fable 与 Haiku 的差别来自为不同任务设计的角色分工，版本新旧不是主要区分。理解这些角色，比记住版本号更有用。

型号名称会随厂商发布节奏变化。选型时应以当前型号说明为准，确认型号是否仍在服务、是否被新版本替代，再用自己的任务分布验证能力边界。
