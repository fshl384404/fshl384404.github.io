## 引言

文件系统层次结构标准（Filesystem Hierarchy Standard，FHS）是 Linux 及类 UNIX 系统中关于文件和目录组织规范的核心标准。当前广泛遵循的版本为 **FHS 3.0（2015 年发布）**，旨在为软件供应商、操作系统创建者和系统管理员提供统一的布局指南。

自 2015 年以来，标准未再更新，而 Linux 发行版在实践中已发生显著演进：systemd 的普及将 `/run` 确立为独立的运行时数据目录；主流发行版（Fedora、Debian、Arch 等）已推行 **usrmerge**，将 `/bin`、`/sbin`、`/lib` 合并至 `/usr` 下的对应目录；容器化与不可变基础设施进一步强化了"静态只读、动态分离"的原则。本文在梳理 FHS 3.0 核心规范的同时，会明确标注这些现代实践，以呈现标准规范与工程实践之间的差异与演进。

---

### FHS 演化简史

| 年份 | 里程碑 | 意义 |
|------|--------|------|
| 1970s | UNIX 诞生 | `/` 存放系统核心，`/usr` 存放用户程序；磁盘容量极小，分区为物理刚需 |
| 1980s | `/usr` 膨胀 | 磁盘容量增长，`/usr` 演变为系统主体，`/bin` 保留最小启动工具集 |
| 1993 | FSSTND 1.0 | Linux 社区首次制定专属标准，解决发行版间目录混乱问题 |
| 1994 | FSSTND → FHS | 吸纳 BSD 社区意见，扩展为跨 UNIX 通用标准 |
| 2000 | FHS 2.3 | 引入 `/media`，替代 `/mnt` 作为可移动介质挂载点 |
| 2012 | Fedora 提议 UsrMove | 首次在主流发行版层面推动 `/bin`、`/sbin`、`/lib` 合并至 `/usr` |
| 2015 | FHS 3.0 | 当前广泛遵循的版本；引入 `/run`，正式承认 systemd 实践 |
| 2016+ | usrmerge 普及 | Debian、Ubuntu、Arch 等主流发行版默认采用统一 `/usr` 布局 |

## 零、一切皆文件

在介绍FHS之前，我们需要先来了解一些Linux文件系统的基础知识，方便我们后续学习。

磁盘在使用前需先进行**分区（Partition）**，将物理磁盘划分为多个逻辑单元。分区格式化后会创建文件系统，其底层空间被划分为固定大小的数据块（Block）——这是文件系统最小的存储单元，通常是 1KB、2KB 或 4KB。而超级块（Superblock）则是在分区最开头，存放整个文件系统整体信息，包括分区总大小、块大小、inode 总数、空闲 inode数、block 总数、空闲块数等。

**文件系统（File‑system）** 是操作系统管理磁盘分区数据的一套规则：负责文件存放、读取、权限管理、磁盘空间分配、目录结构。Linux中的根目录以外的文件要想被访问，需要将其“关联”到根目录下的某个目录来实现，这种关联操作就是“挂载”，这个目录就是“挂载点”，解除次关联关系的过程称之为“卸载”。为了支持不同种类的文件系统，Linux 内核在应用层和底层驱动之间引入了一个抽象层——**虚拟文件系统（VFS，Virtual File System）**。它定义了所有文件系统必须实现的通用接口（如 open、read、write），来屏蔽不同硬件和具体文件系统格式的差异。常见的 Linux 支持多种文件系统类型：

- ext系列：如ext4，主流默认，支持大容量和日志功能。
- XFS：高性能 64 位日志文件系统，擅长处理大文件。
- btrfs：支持快照、压缩和校验，能够快速备份、回滚系统
- 网络/虚拟文件系统：如 proc、sysfs、tmpfs（常驻内存，不占磁盘）。

文件是保存在磁盘上、具备独立 inode 索引的数据集合，存放文本、程序、图片、配置、硬件信息等数据。Linux 遵循"一切皆文件"的设计哲学：目录本质也是一种特殊文件，用于存放文件名到inode的映射。inode（索引节点）是文件的核心底层数据结构，每个文件对应唯一的 inode 编号，储存文件大小、权限、所有者、磁盘数据块地址及时间戳；文件名仅为inode的别名存储在目录文件里。因此，同一inode可以通过多个不同的文件名来访问，这就是硬链接（hard link）。与之相对的是软链接（符号链接），它是一个独立文件，inode 存储的是目标文件的路径字符串，因此可以跨文件系统，也可以指向目录，但删除原始文件后软链接会失效。

Linux 文件类型共七种，不依赖扩展名区分文件类型，后缀仅便于人阅读。使用 `ls -l` 命令的首字符可查看类型（亦可使用file命令或stat命令）：

1. **- 普通文件**：文本、二进制程序、压缩包、日志
2. **d 目录文件**：文件夹
3. **l 软链接（符号链接）**：存储目标路径的引用
4. **b 块设备文件**：硬盘、U 盘等可按块读写的设备，如 `/dev/sda`
5. **c 字符设备文件**：键盘、串口、终端等按字符流读写的设备，如 `/dev/tty`
6. **p 管道文件**：用于进程间通信
7. **s socket 套接字文件**：用于本机进程间通信，如 `mysql.sock`

而命令的后九个字符每三位一组分别表示user(u)所有者、group(g)用户组、other(o)其他用户的权限，其中r=4读；w=2写；x=1执行。

## 一、FHS 的设计哲学与核心原则

### 文件分类的二维矩阵

FHS 依据两个维度对文件系统中的所有文件进行分类：

| 分类维度 | 可共享（Shareable） | 不可共享（Unshareable） |
|----------|---------------------|-------------------------|
| **静态（Static）** | `/usr`、`/opt` | `/etc`、`/boot` |
| **可变（Variable）** | `/var/mail`、`/var/spool/news` | `/var/run`、`/var/lock` |

- **可共享文件**：可在一台主机上保存并在多台主机间使用的文件。
- **不可共享文件**：与特定主机绑定的文件，如设备锁文件、系统特定的内核配置。
- **静态文件**：包含二进制文件、库文件、文档等不经常变动的文件。可保存在只读介质上，备份频率要求较低。
- **可变文件**：非静态文件，内容随系统运行而变化，如日志、缓存、运行时状态。

> 早期 UNIX 在 `/usr` 和 `/etc` 中混合存放静态和可变文件。为实现静态文件只读挂载并简化备份，FHS 设计 `/var` 层次结构，将所有可变文件从 `/usr` 转移至 `/var`，使 `/usr` 可只读挂载。

### 标准的适用范围

FHS 明确以下边界：
- **不强制本地文件的放置位置**：本地站点、发行版、应用程序间的协调由系统管理员自行决定。
- **禁止应用程序在根目录下创建特殊文件或子目录**：FHS 已为各类软件包提供了充足的布局位置。
- **禁止发行版未经审慎考虑在根层次结构下创建新目录**：发行版不应在根层次结构下创建新目录，以避免破坏应用程序的可移植性。

> FHS 是一份人为约定的软件互通规范，Linux 内核本身对目录结构并无硬性约束。NixOS 采用 `/nix/store` 的纯函数式包管理，GoboLinux 重构了整个目录树，这些发行版证明了文件层级可以被重新设计。但出于生态兼容性考量，主流 Linux 发行版仍将 FHS 作为核心参考。

## 二、根文件系统（/）：精简与自足

根文件系统的内容须足以完成系统的**启动、还原、恢复和修复**任务。`/usr`、`/opt` 和 `/var` 可位于其他分区或文件系统上，根分区本身应保持精简。

### 根文件系统保持精简的原因

- 有时需从较小介质上挂载根文件系统；
- 根文件系统包含大量主机特定配置文件（如内核配置、主机名），在网络化系统中不易共享，保持小尺寸可减少不可共享文件导致的空间浪费；
- 根分区磁盘错误导致的数据损坏较其他分区更严重，较小的根文件系统可降低因系统崩溃而损坏的风险；
- 保持小尺寸可兼容分区容量较小的系统环境，避免对开发者存储假设的过度依赖。

### 根目录下必需的目录（FHS 3.0）

| 目录 | 用途 |
|------|------|
| `/bin` | 必需的用户命令二进制文件（所有用户使用） |
| `/boot` | 引导装载程序的静态文件 |
| `/dev` | 设备文件 |
| `/etc` | 主机特定的系统配置 |
| `/lib` | 必需的共享库和内核模块 |
| `/media` | 可移动介质的挂载点 |
| `/mnt` | 临时挂载文件系统用的挂载点 |
| `/opt` | 外部应用程序软件包 |
| `/sbin` | 必需的系统级二进制文件 |
| `/srv` | 本系统所提供服务的数据文件 |
| `/tmp` | 临时文件 |
| `/usr` | 二级层次结构 |
| `/var` | 可变数据 |

> 在已推行 **usrmerge** 的发行版中，`/bin`、`/sbin`、`/lib` 通常是指向 `/usr` 下对应目录的符号链接，不再作为独立的物理目录存在。现代系统同时增加了 /run（tmpfs）、/sys（sysfs）和 /proc（procfs）三个目录，其中 /sys 与 /proc 为虚拟文件系统，/run 为基于内存的临时文件系统。

### 根目录下可选的目录

| 目录 | 用途 |
|------|------|
| `/home` | 用户主目录 |
| `/lib<qual>` | 替代格式的必需共享库（如 `/lib32`、`/lib64`） |
| `/root` | root 用户的主目录 |

## 三、关键目录规范详解

在逐项展开规范之前，以下速查表提供了各目录的类型、持久性与挂载选项的全局视图，便于阅读时对照参考。

| 路径 | 类型 | 持久性 | 典型挂载选项 |
|------|------|--------|--------------|
| `/` | 物理 | 持久 | `rw` |
| `/boot` | 物理 | 持久 | `rw,noauto`（部分场景） |
| `/usr` | 物理/符号链接 | 持久 | `ro`（不可变系统） |
| `/var` | 物理 | 持久 | `rw` |
| `/run` | tmpfs | 易失 | `tmpfs` |
| `/tmp` | tmpfs 或物理 | 易失/定期清理 | `tmpfs` 或 `rw,noexec,nosuid` |
| `/proc` | procfs | 虚拟 | `proc` |
| `/sys` | sysfs | 虚拟 | `sysfs` |

### /bin — 必需的用户命令二进制文件

`/bin` 包含系统管理员与普通用户均可能使用的命令，且这些命令在未挂载其他文件系统时（如单用户模式）必须可用。

**`/bin` 独立于 `/usr/bin` 的历史背景**：早期 UNIX 系统中，`/usr` 常位于独立分区甚至 NFS 上。若系统启动失败进入单用户模式，`/usr` 可能尚未挂载，因此根分区须保留一组最小可用工具（`sh`、`ls`、`mount` 等）。现代 initramfs 已能在早期用户空间加载完整环境，这是 usrmerge 得以推行的技术前提。

**核心要求**：
- `/bin` 下不得包含子目录；
- 必须包含 `sh`，且 `/bin/sh` 若不是真正的 Bourne shell，则须是指向真实 shell 的硬链接或软链接；
- `[` 和 `test` 命令必须一起放置在 `/bin` 或 `/usr/bin` 中（即使由 shell 内部实现，也须以二进制形式提供）。

**代表性命令**：`sh`、`cat`、`cp`、`ls`、`mv`、`rm`、`mkdir`、`mount`、`umount`、`ps`、`sed`、`echo`、`kill`、`pwd`、`sync`。

> usrmerge 后，`/bin` 通常为 `/usr/bin` 的符号链接。

### /sbin — 系统二进制文件

`/sbin` 包含系统管理员使用的工具（及其他仅 root 使用的命令），以及启动、恢复、修复系统所必需的二进制文件。

**区分原则**：若普通用户有时会直接运行某个命令，则它应放在 `bin` 目录而非 `sbin` 目录。普通用户的 `PATH` 中不必包含 `sbin` 目录。

**要求命令**：`shutdown`

**可选命令**：`fdisk`、`fsck`、`fsck.*`、`getty`、`halt`、`ifconfig`、`init`、`mkfs`、`mkfs.*`、`mkswap`、`reboot`、`route`、`swapon`、`swapoff`

> 区分 `/bin` 与 `/sbin` 并非出于安全目的或阻止用户查看操作系统，而是为了明确区分通用命令与系统管理命令。用户应具备对 `/sbin` 下所有内容的读和执行权限。

### /etc — 主机特定的系统配置

`/etc` 层次结构包含配置文件——用于控制程序操作的本地文件。配置文件须为静态文件，不得存放程序主二进制文件。

**名称来源**：`/etc` 的历史命名存在争议（et cetera 与 Editable Text Configuration），FHS 明确定义为"Host-specific system configuration"（主机特定系统配置）。

**关键限制**：
- `/etc` 下不得放置程序主二进制文件（可执行脚本仅限于系统初始化或管理用途）；
- 建议将配置文件保存在 `/etc` 的子目录中，而非直接置于 `/etc` 下。

**重要子目录**：
- `/etc/opt`：外部应用程序软件包的配置文件。安装在 `/opt` 中的软件包，其主机特定配置文件须安装在 `/etc/opt/<subdir>` 中，`<subdir>` 对应于 `/opt` 中该软件包的子树名称。
- `/etc/X11`：X 窗口系统配置文件（如 `Xconfig`、`XF86Config`、`Xmodmap`）。
- `/etc/sgml`：SGML 系统高级参数的通用配置文件。
- `/etc/xml`：XML 系统高级参数的通用配置文件。

**可选配置文件**：`exports`、`fstab`、`group`、`host.conf`、`hosts`、`hosts.allow`、`hosts.deny`、`issue`、`motd`、`networks`、`passwd`、`profile`、`protocols`、`resolv.conf`、`rpc`、`securetty`、`services`、`shells`。

> `mtab` 不符合 `/etc` 的静态特性，保留它属历史原因。现代 Linux 系统中，`/etc/mtab` 通常是指向 `/proc/mounts` 的符号链接。

> **`/etc/os-release` 与 `/usr/lib/os-release` 的关系**：`/etc/os-release` 是系统发行版身份标识的主文件。systemd 类系统优先读取 `/etc/os-release`，若不存在则回退到 `/usr/lib/os-release`。`/etc/os-release` 可能为独立文件（如 Debian/Ubuntu），也可能为指向 `/usr/lib/os-release` 的符号链接（如 Fedora），具体行为因发行版而异。

### /lib — 必需的共享库和内核模块

`/lib` 包含启动系统和运行根文件系统中命令（如 `/bin` 与 `/sbin` 下的二进制文件）所需的共享库镜像。

**要求**：
- 下列文件名模式至少须存在一个：`libc.so.*`（动态链接 C 语言库）、`ld*`（执行时链接器/装载器）；
- 可选子目录：`modules`（可加载内核模块）。

**多架构库布局**：
- **传统 FHS（RHEL/CentOS 风格）**：64 位库位于 `/lib64`，32 位库位于 `/lib`；
- **Multiarch（Debian/Ubuntu 风格）**：库按架构分目录存放，如 `/usr/lib/x86_64-linux-gnu`、`/usr/lib/aarch64-linux-gnu`；
- usrmerge 后，`/lib` 与 `/lib64` 通常指向 `/usr` 下的对应路径。

### /boot — 引导装载程序的静态文件

`/boot` 包含启动过程中所需的所有文件，包括内核、初始 RAM 磁盘（initramfs）和引导管理器配置。它存储内核在执行用户态程序之前所使用的数据。

**特殊选项**：操作系统内核须位于 `/` 或 `/boot`。

> **UEFI 系统中的 `/boot` 布局**：EFI 系统分区（ESP）是 UEFI 引导所必需的。部分发行版（如 Fedora、Arch）将 ESP 直接挂载至 `/boot`，内核与 initramfs 直接存放于 ESP 中；其他发行版（如 Ubuntu、Debian）将 ESP 挂载至 `/boot/efi`，内核与 initramfs 仍位于 `/boot` 下的普通分区中。两种布局各有优劣：前者简化引导管理器与内核的交互，后者保留 `/boot` 分区的独立灵活性。

### /dev — 设备文件

`/dev` 用于放置特殊设备文件。现代 Linux 系统使用 udev（或 systemd-udevd）动态管理设备节点，设备文件在系统运行期间按需创建，而非静态预置。

**Linux 特定要求**：以下设备文件必须存在：
- `/dev/null`：写入数据被忽略，读取返回 EOF；
- `/dev/zero`：输出零数据源；
- `/dev/tty`：进程控制终端的同义词。

> 旧版本曾要求在 `/dev` 下提供 `MAKEDEV` 脚本用于手动创建设备，现代系统已废弃此做法。

### /sys — sysfs虚拟文件系统

`/sys` 是 Linux 内核提供的 sysfs 虚拟文件系统挂载点，用于向用户空间暴露内核数据结构、设备树、总线信息、驱动状态和内核参数。

**主要用途**：
- 查看和修改内核参数（如 `/sys/class/net/eth0/` 下的网卡配置）；
- 电源管理与设备热插拔事件处理；
- 替代部分 `/proc` 中的非进程类信息，使 `/proc` 专注于进程信息。

> sysfs 与 procfs（`/proc`）互补。进程相关信息在 `/proc`，设备和驱动相关信息在 `/sys`。例：查看网卡 eth0 的 MAC 地址使用 `cat /sys/class/net/eth0/address`；查看进程 1 的环境变量使用 `cat /proc/1/environ`。

### /proc — procfs虚拟文件系统

`/proc` 是 procfs 虚拟文件系统的挂载点，提供无需访问设备文件即可与内核交互的机制。

**主要内容**：
- **进程目录**：以 PID 命名的子目录（如 `/proc/1`），包含进程状态、内存映射、文件描述符等信息；
- **系统信息**：`cpuinfo`、`meminfo`、`uptime`、`version` 等只读文件；
- **内核调参**：`/proc/sys/` 下的参数可通过 `sysctl` 实时修改（如 `/proc/sys/net/ipv4/ip_forward`）。

> **与 `/sys` 的区分**：进程相关信息和系统统计归入 `/proc`；设备模型、驱动、总线信息归入 `/sys`。两者互补，共同构成 Linux 用户空间与内核交互的接口。

### /run — 运行时数据

`/run` 是现代 Linux 系统中存放运行时变量数据的标准位置，通常以 tmpfs（内存文件系统，重启后数据丢失）挂载，在系统启动时创建、重启后清空。

**关键规范**：
- PID 文件命名惯例：`<program-name>.pid`（如 `/run/crond.pid`）；
- PID 文件格式：ASCII 编码的十进制进程标识，后跟一个换行符；
- 临时性 UNIX 域套接字应置于此目录；
- `/run` 对未授权用户应为不可写。

> 传统 FHS 将运行时数据置于 `/var/run`。systemd 普及后，`/var/run` 已成为指向 `/run` 的符号链接。新编写的程序应直接使用 `/run`。

### /media 与 /mnt — 挂载点的演进

**`/media`**：包含可移动介质挂载点的目录。若安装了相应子系统，`/media` 下通常有 `usb`、`cdrom`、`sdcard` 等子目录。存在多个同类型设备时，可用数字后缀区分（如 `/media/usb0`、`/media/usb1`），未计数的名称也应保留。

**`/mnt`**：供系统管理员临时挂载文件系统。此目录的内容因环境而异，任何程序的运行方式不应依赖于 `/mnt` 下的内容。此目录不应用于安装程序。

> **演进背景**：在 FHS 2.3 之前，`/mnt` 曾作为所有挂载点的通用目录。FHS 2.3 引入 `/media` 专门用于可移动介质，`/mnt` 被重新定义为临时手工挂载点，两者职责得以分离。

### /tmp — 临时文件

`/tmp` 须为要求临时文件的程序提供存储空间。程序必须假设 `/tmp` 中的任何文件或目录仅用于程序运行期间引用。

> 现代发行版通常将 `/tmp` 挂载为 tmpfs（如 Fedora、Arch），或使用 systemd-tmpfiles 在启动时及定期清理（如 RHEL/Debian）。无论采用何种方式，`/tmp` 中的数据均不应被视为永久存储。

### /opt — 外部应用程序软件包

`/opt` 保留用于安装外部（第三方）应用程序软件包。每个软件包须安装在独立的目录树中：

```
/opt/<package>/
/opt/<provider>/
```

其中 `<package>` 为描述软件包的名称，`<provider>` 为软件提供者的 LANANA（Linux 命名与编号管理局）注册名称。

**关键规则**：
- 静态文件位于 `/opt/<package>` 或 `/opt/<provider>` 下；
- 可变文件须位于 `/var/opt/<subdir>` 下；
- 主机特定配置文件须位于 `/etc/opt/<subdir>` 下；
- `/opt/bin`、`/opt/doc`、`/opt/include`、`/opt/info`、`/opt/lib` 和 `/opt/man` 保留给本地系统管理员使用；
- 用户调用的程序须位于 `/opt/<package>/bin` 或 `/opt/<provider>` 层次下；
- 发行版可将软件安装至 `/opt`，但未经本地系统管理员同意不得修改或删除本地管理员安装的软件。

> Flatpak 应用运行于沙箱中，其数据位于 `~/.var/app/<app-id>`，配置位于 `~/.config`，与 FHS 的 `/opt` 逻辑相似但隔离性更强。Snap 使用 `/snap` 目录（非 FHS 标准），反映了传统 FHS 在应用沙盒时代的局限性。

### /srv — 本系统所提供服务的数据文件

`/srv` 包含由系统提供的站点特定数据。此目录旨在使用户能够找到特定服务的数据文件位置。

**注意事项**：
- `/srv` 下子目录的命名方法尚未标准化，可按协议（如 `ftp`、`www`、`cvs`）或管理内容（如 `/srv/physics/www`）归类；
- 任何程序不应依赖 `/srv` 下特定的子目录结构；
- 发行版须注意不要在未经管理员允许的情况下删除这些目录中的文件。

### /home 与 /root — 用户主文件夹

**`/home`**：用户主目录是站点特定的文件系统位置。程序不应依赖此固定路径（应使用 `getpwent(3)` 库函数查找用户主目录）。

- 应用程序的用户特定配置应保存在用户主目录下以 `.` 开头的文件（"点文件"）中；
- 若应用程序需创建多个点文件，应置于以 `.` 开头的子目录（点目录）中，配置文件本身不应以 `.` 开头。

**`/root`**：root 账户的主目录可由开发者或本地偏好设定，但 `/root` 为推荐的默认位置。如果 root 账户的主目录不在根文件系统上，系统应在无法找到的情况下默认定位至 `/`。

> 不建议使用 root 账户执行普通用户可以完成的任务。root 账户的主目录下不应存放邮件和其他应用的子目录；发给管理员（如 root、postmaster、webmaster）的邮件应转发给合适的普通用户。

## 四、/usr 层次结构

`/usr` 是文件系统中的第二个重要部分，承载可共享的只读数据。`/usr` 应在各类 FHS 兼容主机之间共享且禁止写入。任何主机特有信息或随时间变化的量应保存在其他位置。

### 核心特征

- 可在各类 FHS 兼容主机之间共享；
- 禁止写入操作；
- 大型软件包禁止在 `/usr` 根目录下直接创建子目录（X 窗口系统除外）；
- 历史兼容性符号链接（现已不常用）：`/usr/spool -> /var/spool`、`/usr/tmp -> /var/tmp`、`/usr/spool/locks -> /var/lock`。

### 必需的子目录

| 目录 | 用途 |
|------|------|
| `/usr/bin` | 绝大多数用户命令 |
| `/usr/include` | C 程序包含的头文件 |
| `/usr/lib` | 编程和软件包的库 |
| `/usr/local` | 本地层次结构（系统安装后为空） |
| `/usr/sbin` | 非关键的标准系统二进制文件 |
| `/usr/share` | 与架构无关的数据 |

> usrmerge 后，`/bin`、`/sbin`、`/lib` 均已合并至 `/usr` 下的对应目录，这是现代发行版的默认布局。

### /usr/bin 与 /usr/sbin：命令放置的决策规则

**`/usr/bin`**：包含非关键的命令二进制文件。仅非 root 用户需要的项目（如 X 窗口系统）通常不必放置在根分区。

若安装了相应子系统，`/usr/bin` 中应有：`perl`、`python`、`tclsh`、`wish`、`expect`。这些可以是指向实际解释器位置的符号链接。

**`/usr/sbin`**：包含任何系统管理员单独使用的非关键二进制文件。系统修复、还原、挂载 `/usr` 等关键功能的系统管理程序应放在 `/sbin` 下。本地安装的系统管理程序应位于 `/usr/local/sbin` 下。

### /usr/libexec — 内部程序

`/usr/libexec` 用于存放不被用户直接调用、也不被其他软件包直接调用的二进制文件，通常是某些守护进程或框架的内部辅助程序（如邮件投递代理、桌面环境内部组件）。

FHS 3.0 正式引入此目录，旨在使 `/usr/lib` 专注于共享库，避免混杂可执行程序。

> **注意**：并非所有发行版均采纳 `/usr/libexec`。Debian/Ubuntu 等发行版倾向于将内部二进制文件直接置于 `/usr/lib/<package>/` 目录下。在编写跨发行版兼容的软件时，建议通过构建系统检测或运行时回退机制处理此差异。

### /usr/local — 本地软件

`/usr/local` 层次结构用于系统管理员安装本地软件，在系统升级时应保证安全、不被覆盖。它可用于存放可在主机组间共享但不在 `/usr` 中的程序和数据。

**关键原则**：
- 本地安装的软件必须位于 `/usr/local`，而非 `/usr`，除非有意替换或升级 `/usr` 中的软件；
- 系统安装完成后，`/usr/local` 下只应存在以下标准子目录（可为空）：`bin`、`etc`、`games`、`include`、`lib`、`man`、`sbin`、`share`、`src`。本地管理员不应在此处创建非标准目录名。

> 注意：`/usr/etc` 仍不允许使用——`/usr` 中的程序应将配置文件置于 `/etc` 下。

> **容器场景下的语义变化**：在 OCI 容器镜像中，`/usr/local` 通常与 `/usr` 一同作为镜像只读层的一部分，失去了"本地管理员覆盖"的原始语义。建议容器镜像将应用安装至 `/usr` 下的专用路径（如 `/usr/bin`），而非依赖 `/usr/local`，以避免与宿主机路径混淆。

### /usr/share — 架构无关数据

`/usr/share` 存放只读、与架构无关的数据文件，通常可在同一操作系统的不同架构间共享（如 x86_64 与 ARM64 平台共享一个集中挂载的 `/usr/share`）。但一般不应在不同操作系统或相同操作系统的不同版本间共享。

**内容类型**：
- 手册页（`/usr/share/man`）
- 单词列表（`/usr/share/dict`）
- 时区信息（`/usr/share/zoneinfo`）
- 区域信息（`/usr/share/locale`）
- SGML/XML 数据

手册页按语言和章节分目录存放，遵循 `<mandir>/<locale>/man<section>/` 的层次结构，其中 `<locale>` 基于 POSIX 标准，`<section>` 对应传统手册页章节（1-8）。

### /usr/src — 源代码

源代码可置于 `/usr/src` 中，仅用作参考。通常此层次结构下不应进行源文件编译——构建工作应在用户主目录或 `/usr/local/src` 等位置进行。

## 五、/var 层次结构

`/var` 包含可变数据文件，包括 spool（缓冲区/队列）目录、管理和日志数据，以及过渡和临时文件。`/var` 的详细规定使得 `/usr` 可以以只读方式挂载。

### 核心要求

| 目录 | 用途 |
|------|------|
| `/var/cache` | 应用程序缓存数据 |
| `/var/lib` | 可变状态信息 |
| `/var/local` | `/usr/local` 的可变数据 |
| `/var/lock` | 锁文件（现代系统通常指向 `/run/lock`） |
| `/var/log` | 日志文件和目录 |
| `/var/opt` | `/opt` 的可变数据 |
| `/var/run` | 运行时数据（现代系统通常指向 `/run`） |
| `/var/spool` | 应用程序 spool 数据 |
| `/var/tmp` | 系统两次启动之间保留的临时文件 |

> 通常禁止应用程序在 `/var` 顶层直接添加目录。只有在对整个系统具有普遍意义的情况下才允许创建此类目录。

### /var/run — 运行时数据

传统上，此目录包含描述系统启动以来的运行时信息，须在启动过程初期清除。

> systemd 及现代发行版中，`/var/run` 已是指向 `/run` 的符号链接（该行为由 systemd 启动逻辑或发行版基础包实现，不同发行版在具体机制上略有差异，但最终效果一致）。新程序应直接写入 `/run`。

### /var/log — 系统活动日志

此目录包含各类日志文件，绝大多数日志应写入此目录或其子目录。

**标准文件**：
- `lastlog`：每位用户上次登录的记录
- `messages` 或 `syslog`：传统系统日志（由 rsyslog 等产生）
- `wtmp`：所有登录和注销的记录

> **systemd-journald 的持久化行为**：`journald` 的持久化日志依赖于 `/var/log/journal/` 目录是否存在——若存在则启用持久化，否则日志仅保存在 `/run/log/journal/`（易失性）。大多数桌面/服务器发行版默认创建此目录，而容器镜像或最小化安装可能不创建。

### /var/spool — 待处理数据的队列

`/var/spool` 包含正在等待后续处理的数据，表示工作将由程序、用户或管理员在以后完成；处理完成后这些数据通常会被删除。

**可选子目录**：
- `lpd`：打印机 spool 目录（锁文件 `lpd.lock` 必须位于此）
- `mqueue`：寄出邮件队列
- `news`：新闻 spool 目录
- `uucp`：UUCP 的 spool 目录

### /var/lib — 可变状态信息

`/var/lib` 保存属于应用程序或系统的状态信息。状态信息是程序运行时会修改的、属于特定主机的信息。禁止用户修改 `/var/lib` 中的信息来配置软件包的操作方式。

状态信息通常用于保持一个（或一组内部相关的）应用程序多次调用和不同实例之间的状态，重启后依然有效，不应是日志输出或 spool 数据。

**要求子目录**：`misc`（混杂的状态数据）

**可选子目录**：
- `<editor>`：编辑器备份文件和状态（如 `vim`、`emacs` 的崩溃恢复文件）
- `<package>`：包和子系统的状态数据
- `hwclock`：`hwclock` 的状态目录（存放 `adjtime` 文件）
- `xdm`：X 显示管理器可变数据

### /var/cache — 应用程序缓存数据

`/var/cache` 用于存放应用程序的缓存数据，这些数据由本地计算机上耗时的 I/O 操作或计算生成。应用程序必须能够重新生成或还原这些数据。

**关键特征**：
- 缓存文件可被删除而不会造成数据损失；
- 应用程序必须能恢复被手动删除的缓存文件；
- 与 `/var/spool` 不同，缓存文件在两次应用程序调用或重启间应保持有效；
- 系统管理员可对 `/var/cache` 采取与 `/var` 其他目录不同的磁盘和备份策略。

**可选子目录**：`fonts`（本地生成的字体）、`man`（本地格式化的手册页）、`www`（WWW 代理或缓存数据）。

### /var/mail — 邮箱文件

须通过 `/var/mail` 访问邮件 spool，邮件 spool 文件须采用 `<username>` 的形式，以标准 UNIX 邮箱格式保存。

> 此目录的逻辑位置从 `/var/spool/mail` 修改为 `/var/mail`，是为了使 FHS 与主流 UNIX 安装版本保持兼容，便于在多主机间共享 `/var/mail`。

### /var/tmp 与 /tmp — 临时文件的持久性区分

| 特性 | `/tmp` | `/var/tmp` |
|------|--------|------------|
| **持久性** | 通常在系统启动时清空 | 系统重启间保留 |
| **用途** | 程序运行时的临时文件 | 要求在两次系统启动间保留的临时文件 |
| **清理频率** | 建议每次启动时删除 | 建议删除频率低于 `/tmp` |

> `/var/tmp` 下保存的数据比 `/tmp` 中的更持久。系统重新启动时**禁止**删除 `/var/tmp` 下的文件和目录。

## 六、usrmerge：传统目录的合并

usrmerge 是主流发行版已推行的实践，将根目录下的传统目录合并至 `/usr` 中：

| 传统路径 | usrmerge 后 |
|---------|------------|
| `/bin` | `/usr/bin` 的符号链接 |
| `/sbin` | `/usr/sbin` 的符号链接 |
| `/lib` | `/usr/lib` 的符号链接 |
| `/lib64` | `/usr/lib64` 的符号链接（若存在） |

**优势**：
- 简化快照与回滚（`/usr` 可作为原子单元管理）；
- 便于只读挂载整个操作系统层次结构；
- 与 initramfs 配合，早期用户空间即可访问完整工具链；
- 消除 `/bin` 与 `/usr/bin` 的冗余，降低维护成本。

**技术前提**：initramfs 的普及使得早期用户空间即可加载完整 `/usr` 内容，传统上"根分区必须包含最小可用环境"的约束已大幅放松。

> usrmerge 并非 FHS 3.0 的正式要求。在编写跨发行版脚本时，应避免假设 `/bin` 与 `/usr/bin` 为物理分离的目录。

---

## 七、systemd 与 /run 的演进及日志体系

systemd 的引入对 FHS 的现代实践产生了深远影响，主要体现于运行时数据目录的独立化和日志体系的统一化。

### /run 的独立化

在 FHS 3.0 之前，运行时数据（PID 文件、套接字等）约定存放于 `/var/run`。但 `/var` 通常为持久存储，其目录结构在系统启动早期可能尚未就绪。systemd 在启动早期创建 `/run`（tmpfs），用于存放所有易失性运行时数据，并自动将 `/var/run` 创建为指向 `/run` 的符号链接。

这一演进解决了以下问题：
- **启动时序依赖**：运行时数据不再依赖 `/var` 的挂载状态；
- **数据隔离**：tmpfs 确保重启后运行时数据自动清空，无需额外清理脚本；
- **权限控制**：`/run` 可更精细地设置访问权限（如 `/run/user/<uid>` 用于用户级运行时目录）。

### systemd-journald 的日志存储

systemd 引入 `journald` 作为系统日志的集中收集服务，其存储位置遵循以下规则：
- 若 `/var/log/journal/` 目录存在，日志以二进制格式持久化存储于此；
- 若该目录不存在，日志仅保存在 `/run/log/journal/`（易失性），重启后丢失。

多数桌面与服务器发行版默认创建 `/var/log/journal/` 以启用持久化日志，而容器镜像或最小化安装通常不创建此目录，以避免对持久存储的依赖。`journald` 与传统 syslog 可共存，许多发行版同时保留 rsyslog 以兼容旧有工具。

## 八、现代发行版完整目录结构一览

```
├── bin -> usr/bin          (usrmerge)
├── boot
├── dev
├── etc
├── home
├── lib -> usr/lib          (usrmerge)
├── lib64 -> usr/lib64      (usrmerge, 若适用)
├── media
├── mnt
├── opt
├── proc                    (procfs)
├── root
├── run                     (tmpfs, 运行时数据)
├── sbin -> usr/sbin        (usrmerge)
├── srv
├── sys                     (sysfs)
├── tmp                     (tmpfs 或物理存储)
├── usr
│   ├── bin
│   ├── include
│   ├── lib
│   ├── libexec             (部分发行版)
│   ├── local
│   ├── sbin
│   ├── share
│   └── src
└── var
    ├── cache
    ├── lib
    ├── log
    ├── run -> ../run       (符号链接)
    ├── spool
    └── tmp
```

上述结构为 FHS 3.0 与 usrmerge 的综合呈现。具体发行版可能存在偏差（如 `/libexec` 的存废、`/boot` 的 UEFI 挂载方式），应以实际系统为准。

## 九、FHS 的工程实践

### 软件安装决策树

| 场景 | 目标路径 | 配置路径 | 数据路径 |
|------|----------|----------|----------|
| 发行版官方包 | `/usr` | `/etc` | `/var/lib` |
| 第三方商业软件 | `/opt/<package>` | `/etc/opt/<package>` | `/var/opt/<package>` |
| 本地手动编译 | `/usr/local` | `/usr/local/etc` | `/var/local` |
| 用户个人程序 | `~/.local` | `~/.config` | `~/.local/share` |
| 容器镜像 | `/usr`（只读层） | `/etc`（可写层） | `/var`（卷挂载） |

### 分区规划建议

基于 FHS 的二维分类与现代实践，推荐以下分区策略：

| 挂载点 | 文件类型 | 建议 |
|--------|----------|------|
| `/` | 不可共享、部分静态/可变 | 保持最小化；usrmerge 后需包含完整 `/usr` |
| `/var` | 可共享/不可共享、可变 | 独立分区以防止日志撑满根分区 |
| `/home` | 可共享、可变 | 通常独立分区，便于备份与共享 |
| `/tmp` | 不可共享、可变 | 建议挂载为 tmpfs 或由 systemd-tmpfiles 管理 |
| `/boot` | 不可共享、静态 | 独立小分区；UEFI 环境下可为 EFI 系统分区或独立 `/boot` 分区 |
| `/run` | 不可共享、可变 | 系统自动挂载为 tmpfs，无需手动分区 |

### 容器与不可变系统场景

**不可变发行版**（如 Fedora Silverblue、openSUSE MicroOS）：将 `/usr` 设为只读，`/etc` 可写覆盖，`/var` 存放动态数据。这本质上是 FHS"静态/可变分离"原则的极致化。`/etc` 中的覆盖机制（如 `conf.d` 目录和 `.rpmnew` 文件）用于在只读 `/usr` 基础上提供本地配置覆盖。

**容器镜像（OCI）**：`/usr` 作为只读镜像层，`/etc` 和 `/var` 通过 OverlayFS 或卷（volume）覆盖。容器的轻量隔离使得 `/proc`、`/sys` 等目录的命名空间隔离带来了新的语义变化——例如容器内的 `/proc` 仅反映容器自身的进程树，而非宿主机全局进程。

---

## 结语

FHS 标准通过规范文件系统的目录结构，解决了软件可预测性、系统可维护性和跨平台兼容性等核心问题。其设计哲学——通过**可共享/不可共享**与**静态/可变**的二维分类管理文件——使系统管理员能够合理规划存储布局、制定差异化的备份策略。

自 FHS 3.0（2015 年）发布以来，Linux 生态系统已发生深刻变化：systemd 带来了 `/run` 的独立与日志体系的统一，usrmerge 消解了 `/bin` 与 `/usr/bin` 的历史分隔，容器化与不可变基础设施进一步强化了"静态只读、动态分离"的原则。理解 FHS 不仅有助于系统管理员在分区规划、故障恢复和系统迁移中做出正确决策，也为软件开发人员提供了明确的文件放置指导。在遵循标准的同时关注现代发行版的实际演进，是标准规范与工程实践之间寻求最佳平衡的必要路径。
